### 二、AdamW 为什么这么吃显存？

教授打开之前的代码：

```python
optimizer = torch.optim.AdamW(    model.parameters(),    lr=3e-4)
```

“还记得 AdamW 吗？”

林默回答：

“它会保存梯度的一阶矩和二阶矩估计。”

“没错。”

假设我们进行常规 FP32 全参数训练，暂时不考虑激活和其他开销。

每个参数可能涉及：

| 内容        | 每参数字节数 |
| --------- | ------ |
| FP32 参数   | 4      |
| FP32 梯度   | 4      |
| AdamW 一阶矩 | 4      |
| AdamW 二阶矩 | 4      |
| 合计        | 16     |

所以 7B 模型：

\[ 7\times10^9\times16 = 112\text{ GB} \]

7B 模型：简化 FP32 AdamW 状态预算（十进制 GB）

| 状态 | 每参数字节 | 7B 参数理论占用 |
| --- | --- | --- |
| FP32 权重 | 4 | 28 GB |
| FP32 梯度 | 4 | 28 GB |
| FP32 一阶矩 | 4 | 28 GB |
| FP32 二阶矩 | 4 | 28 GB |
| 合计 | 16 | 112 GB（约 104.3 GiB） |

只计算指定状态，不含激活、临时工作区、缓存及其他开销；不是所有混合精度实现的通用公式，也不是显存实测。

“而且这个 112GB 并不是所有混合精度训练的固定显存公式。”

“不同的混合精度方案，可能保存不同精度的参数副本、梯度和优化器状态。”

“实际内存预算必须根据具体实现计算。”

### 三、为什么 Batch Size 降到 1 也不一定有用？

“Batch Size 主要影响中间激活和输入数据。”

教授点头。

这就是大模型训练中非常重要的区分：

参数相关显存主要取决于模型大小、数据精度以及优化器设计。

激活相关显存主要受到 Batch Size、Sequence Length、隐藏维度、网络层数和算子实现影响。

所以：

```text

    │      ↓

    │
    ├── 中间激活过大？
    │      ↓
    │   减小 Batch、Checkpointing
    │

```

“你必须先知道是谁占用了显存。”

“才能选择正确的武器。”

## 第二幕：混合精度——让数字穿上轻甲

### 四、FP32、FP16、BF16 到底是什么？

教授在白板上写下三个名字。

```text
FP32

FP16

BF16
```

林默说：

“都是浮点数。”

“但分别有什么区别？”

教授回答：

“浮点数在计算机里，通常不是直接存储一个普通的十进制小数。”

“它会使用符号位、指数和有效数字字段来近似表示实数。”

三种格式的典型布局：

| 格式 | 总位数 | 符号位 | 指数位 | 尾数字段 |
| --- | --- | --- | --- | --- |
| FP32 | 32 | 1 | 8 | 23 |
| FP16 | 16 | 1 | 5 | 10 |
| BF16 | 16 | 1 | 8 | 7 |

尾数字段不包含规范化浮点数的隐含前导有效位。

林默仔细看。

“FP16 和 BF16 都是 16 位。”

“但 FP16 给了尾数更多位。”

“BF16 给了指数更多位？”

教授点头。

### 五、指数位与尾数位分别决定什么？

教授拿出一个比喻。

“假设你要记录天文学距离和实验室测量数据。”

“指数位更多，意味着能表示更大或更小量级的数字。”

“有效数字位更多，意味着在某个量级附近能区分更细小的数值差异。”

因此：

| 格式   | 存储空间 | 动态范围          | 有效精度 |
| ---- | ---- | ------------- | ---- |
| FP32 | 4 字节 | 大             | 高    |
| FP16 | 2 字节 | 较窄            | 中等   |
| BF16 | 2 字节 | 接近 FP32 的指数范围 | 较低   |

林默问：

“所以 BF16 更适合大模型训练？”

教授说：

“在支持 BF16 高效运算的硬件上，它通常是非常有吸引力的选择。”

“因为它具有接近 FP32 的动态范围，能减少 FP16 常见的数值溢出或下溢风险。”

“但 BF16 不是万能的。它的有效精度比 FP16 更低，某些操作仍需更高精度。”

### 六、为什么不能把所有东西都强制转成 FP16？

林默敲下：

```python
model = model.half()
```

又把输入转成 FP16。

“这样不就省显存了？”

教授立即阻止。

“这属于手动降低参数精度，不等于安全的自动混合精度训练。”

因为有些操作适合低精度，例如：

```text
大规模矩阵乘法
```

但有些操作对数值范围和精度更敏感，例如某些：

```text
归一化
损失计算
归约计算
```

如果全部粗暴地使用 FP16，可能出现：

```python
Loss = NaN

Gradient = Inf

训练突然发散
```

教授写下：

**Automatic Mixed Precision**

简称：

AMP。

“它的核心思想是，让不同操作根据实现策略使用适合的数值精度，而不是所有运算都一刀切。”

### 七、PyTorch 的 `autocast`

教授开始编写一个标准 CUDA 混合精度训练循环：

```python
# 需要支持 BF16 的 CUDA GPU，以及已经定义的 MyModel、loader、loss_fn。
device = torch.device("cuda")
model = MyModel().to(device)
optimizer = torch.optim.AdamW(model.parameters(), lr=3e-4)
model.train()
for x, y in loader:
    x, y = x.to(device), y.to(device)
    optimizer.zero_grad(set_to_none=True)
    with torch.autocast(device_type="cuda", dtype=torch.bfloat16):
        logits = model(x)
        loss = loss_fn(logits, y)
    loss.backward()
    optimizer.step()
```

林默盯着：

```python
with torch.autocast(device_type="cuda", dtype=torch.bfloat16):
    ...  # 在此执行前向传播和 Loss 计算
```

“所以在这个区域里，PyTorch 会按 AMP 的规则选择运算精度？”

“对。”

“注意，这不是把模型所有权重永久变成 BF16。”

“常见 AMP 训练仍然会保留 FP32 参数，优化器也可能使用 FP32 状态。”

这与：

```python
model.to(torch.bfloat16)
```

并不是一回事。

### 八、GradScaler 为什么存在？

林默翻看其他人的代码。

突然发现：

```python
scaler = torch.amp.GradScaler("cuda")
```

“教授，为什么有些训练还多一个 `GradScaler`？”

教授在黑板上写：

```text
原始梯度：

0.00000001
```

“如果 FP16 无法充分表示某些非常小的梯度，它们可能下溢为零。”

“于是我们可以在反向传播之前，暂时把 Loss 放大。”

例如：

\[ L'=1024L \]

那么：

\[ \frac{\partial L'}{\partial w} = 1024\frac{\partial L}{\partial w} \]

林默明白了。

“这样梯度也放大了。”

“对。”

“然后参数更新之前，再把梯度缩回去。”

这就是 Loss Scaling 的核心思路。

FP16 AMP 训练中常见：

```python
# 假设 model、optimizer 已创建并位于 CUDA，loader 与 loss_fn 已定义。
scaler = torch.amp.GradScaler("cuda")
model.train()
for x, y in loader:
    x, y = x.to("cuda"), y.to("cuda")
    optimizer.zero_grad(set_to_none=True)
    with torch.autocast(device_type="cuda", dtype=torch.float16):
        logits = model(x)
        loss = loss_fn(logits, y)
    scaler.scale(loss).backward()
    scaler.step(optimizer)
    scaler.update()
```

教授说：

“`GradScaler` 还会监测非有限梯度，并在必要时跳过参数更新和调整缩放比例。”

“BF16 通常不需要通过这种方式解决 FP16 的梯度下溢问题。”

林默在笔记中写下：

> autocast 负责运算精度策略；GradScaler 主要服务于 FP16 梯度数值稳定性。

## 第三幕：梯度累积——没有大货车，就多运几趟

```text

```

林默问：

“那我是不是没办法训练？”

教授笑了。

“你想想，训练过程中最关键的参数更新发生在哪一步？”

林默回答：

```text
optimizer.step()
```

“对。”

“那假设我们不每处理一批就更新，而是先累积多个 Batch 的梯度呢？”

林默突然想起第一章。

> PyTorch 的 `.grad` 默认会累加！

### 十、原来梯度累积利用的是第一章的知识

正常训练：

```text
Batch 1
   ↓
backward()
   ↓
optimizer.step()

Batch 2
   ↓
backward()
   ↓
optimizer.step()
```

而梯度累积：

```text
Batch 1
   ↓
backward()
   │
   │ 不更新参数
   ▼
Batch 2
   ↓
backward()
   │
   │ 不更新参数
   ▼
Batch 3
   ↓
backward()
   │
   │ 不更新参数
   ▼
Batch 4
   ↓
backward()
   │
   ▼
optimizer.step()
```

林默眼睛亮了。

“所以我每次只喂 4 条数据。”

“连续累积 16 次。”

“就相当于一次用 64 条数据计算梯度？”

教授回答：

“在满足相应条件时，可以得到与更大 Batch 相同或非常接近的平均梯度。”

“但你需要处理好 Loss 缩放。”

### 十一、为什么 Loss 要除以累积步数？

假设：

```python
micro_batch_size = 4

accumulation_steps = 16
```

有效 Batch Size：

\[ 4\times16=64 \]

正常情况下，我们希望得到 64 个样本的平均梯度：

\[ g=\frac1{64}\sum_{i=1}^{64}g_i \]

每个 Micro-Batch 的 Loss 如果已经是四个样本的平均值，那么它的梯度是：

\[ g_j=\frac14\sum_{i\in B_j}g_i \]

16 个 Batch 梯度直接累加：

\[ \sum_{j=1}^{16}g_j \]

会比所需的整体平均梯度大 16 倍。

因此：

```python
loss = loss / accumulation_steps
```

教授写：

```python
# 这里恰好累积 16 个同样大小、等权的 Micro-Batch。
accumulation_steps = 16
optimizer.zero_grad(set_to_none=True)
for step in range(accumulation_steps):
    x, y = get_batch()
    x, y = x.to(device), y.to(device)
    logits, loss = model(x, y)
    (loss / accumulation_steps).backward()
optimizer.step()
```

林默点头。

“这样累积的梯度才对应整体平均梯度。”

教授补充：

“这个例子假设各 Micro-Batch 大小相同，Loss 按样本平均，且没有影响 Batch 间等价性的特殊操作。”

“如果最后一批大小不同，或者 Loss 按 Token 平均且有效 Token 数不同，应该按实际样本数或有效 Token 数加权。”

### 十二、把训练配置写成一张估算表

教授把原来的计算表打印出来。

“先手算几组配置，看看我们到底改变了什么。”

| 每卡 Micro-Batch | 累积步数 | 数据并行 GPU 数 | 每次更新的有效样本数 |
| --- | --- | --- | --- |
| 4 | 16 | 1 | 64 |
| 2 | 32 | 1 | 64 |
| 4 | 8 | 2 | 64 |

有效样本数 = 每卡 Micro-Batch × 累积步数 × 数据并行卡数。

这张表不是显存测量结果。前两组虽有相同的有效样本数，单次激活需求与运行开销可能不同；模型权重和优化器状态也不会随 Micro-Batch 同比例缩小。第三组假设各数据并行副本处理等量独立样本，不能把张量并行卡数直接代入。

对于变长文本，Loss 若按有效 Token 平均，应在整个累积窗口按有效 Token 总数归一化；简单把每个 Micro-Batch 的均值除以累积步数，可能产生不同的加权。遍历 DataLoader 时，最后不足一个累积窗口的数据也应提交更新，并按实际样本或 Token 数归一化。配合 AMP 时，应在完整窗口累积结束后再 unscale、裁剪、step 与更新 scaler。

### 十三、梯度累积真的完全等价于大 Batch 吗？

林默突然问：

“那如果完全一样，为什么不永远用 Micro-Batch Size = 1？”

教授摇头。

“因为它们不一定完全等价。”

可能的差异包括：

- BatchNorm 等依赖当前批次统计的操作。
- Dropout 等随机操作产生不同的随机掩码。
- 浮点数计算顺序不同导致数值误差。
- Batch 间长度和有效 Token 数不同造成 Loss 加权问题。
- 多次小 Batch 前向传播带来额外运行开销。

“而且，”教授继续，“梯度累积主要降低单次前向、反向计算所需的激活显存。”

“它不会自动减少模型参数、梯度 Tensor 和 AdamW 状态所占用的内存。”

林默终于明白了：

> 梯度累积解决的是无法一次放下大 Batch 的问题，不是万能显存压缩技术。

## 第四幕：梯度检查点——忘记过去，必要时重新计算

### 十四、显存里最昂贵的记忆

教授重新打开 Transformer。

```text
Transformer Block 1
        ↓
Transformer Block 2
        ↓
Transformer Block 3
        ↓
...
        ↓
Transformer Block 32
```

“你还记得为什么前向传播需要保存激活吗？”

林默回答：

“因为反向传播要用中间结果计算梯度。”

教授点头。

普通训练：

```text
Forward
   │
   ├── 保存 Block 1 中间激活
   ├── 保存 Block 2 中间激活
   ├── 保存 Block 3 中间激活
   │
   └── 保存 Block 32 中间激活
              │
              ▼
           Backward
```

“可是，”教授问，“如果显存装不下全部激活怎么办？”

林默说：

“那就少保存？”

“对。”

“但是反向传播需要它们。”

林默皱眉。

教授笑了。

“所以——”

> 需要的时候重新计算。

### 十五、Activation Checkpointing 的核心思想

教授画了两条路径。

普通反向传播

Block 1

保存激活

Block 2

保存激活

Block 3

保存激活

Backward

保存更多中间结果，减少反向阶段的重复计算。

Activation Checkpointing

Block 1

保存检查点

Block 2

少保存中间激活

Block 3

反向时重新计算

Backward

减少保存的激活，以反向阶段更多计算为代价。

林默突然笑了。

“这不就是计算机系统里经典的时间换空间？”

教授点头。

“完全正确。”

普通训练：

```text
保存更多结果
    ↓
更多显存
    ↓
减少重复计算
```

Checkpointing：

```text
保存更少结果
    ↓
节省显存
    ↓
反向时重新计算
```

### 十六、PyTorch 如何使用 Checkpoint？

教授写：

```python
from torch.utils.checkpoint import checkpoint
```

假设我们有多个 Transformer Block：

```python
for block in self.blocks:
    x = checkpoint(block, x, use_reentrant=False)
```

林默问：

“所以不是把数据写入磁盘？”

“不是。”

“这里的 Checkpointing 不是我们平时说的保存模型训练进度。”

教授特别区分：

```text
Activation Checkpointing
→ 减少反向传播需要保存的中间激活


Model Checkpoint
→ 保存模型参数、优化器状态等
→ 用于训练恢复或部署
```

名字接近，但目的不同。

### 十七、为什么不是所有地方都开启 Checkpointing？

林默说：

“既然能省显存，那我全部开启不就行了？”

教授问：

### 十九、LoRA 的核心：原来的权重不动，只学习改变量

教授回到第二章的 `nn.Linear`。

一个线性层：

\[ y=Wx \]

假设：

\[ W\in\mathbb{R}^{4096\times4096} \]

这个矩阵有多少参数？

\[ 4096^2=16,777,216 \]

约 1678 万。

如果直接全参数微调，就需要对整个 W 计算并保存梯度，并为它维护优化器状态。

教授说：

“但我们可以冻结 W。”

```text
W.requires_grad_(False)
```

“然后为它添加一个额外的可训练变化量。”

原来的计算：

\[ y=Wx \]

改成：

\[ \boxed{y=(W+\Delta W)x} \]

其中：

- \(W\)：冻结的预训练权重。
- \(\Delta W\)：需要学习的权重变化量。

林默问：

“可是 \(\Delta W\) 不也是一个 4096×4096 的矩阵吗？”

### 二十、低秩分解：让两个小矩阵代替一个大矩阵

教授写：

\[ \Delta W=BA \]

其中：

\[ A\in\mathbb{R}^{r\times4096} \]

\[ B\in\mathbb{R}^{4096\times r} \]

这里：

\[ r\ll4096 \]

通常选择比较小的 Rank。

例如：

\[ r=16 \]

那么：

```text
原始权重矩阵 W

4096 × 4096

冻结，不训练
```

而：

```text
LoRA A

16 × 4096
```

```text
LoRA B

4096 × 16
```

参与训练。

整个计算：

\[ \boxed{y=Wx+BAx} \]

林默盯着公式。

“所以 W 不动。”

“但 BA 会不断学习如何修正它的输出？”

教授点头。

\[ \frac{131072}{16777216}\times100\% = 0.78125\% \]

一个 4096×4096 Linear 层的可训练参数对比

16,777,216

131,072

仅针对这个无偏置 Linear 权重矩阵进行的比较，不代表整个模型的 LoRA 参数比例或总显存节省比例。

“所以 LoRA 能大幅降低可训练参数及相关优化器状态的开销，但不能简单说总显存降低 99%。”

\[ W'=W+BA \]

“训练期间只改变 A 和 B。”

```text
        │
        ├── 保持冻结
        │
```

## 第六幕：亲手实现 LoRA

### 二十三、其实不需要神秘的框架

林默问：

“教授，LoRA 看起来像很复杂的论文技术。”

“但 PyTorch 能自己写吗？”

教授点头。

“如果你真正理解 `nn.Linear`、`nn.Parameter` 和反向传播，LoRA 的核心其实不复杂。”

他开始编写。

```python
import math
import torch
import torch.nn as nn
import torch.nn.functional as F

class LoRALinear(nn.Module):
    def __init__(self, original_linear, rank=16, alpha=32):
        super().__init__()
        if rank < 1:
            raise ValueError('rank must be positive')
        self.original = original_linear
        for param in self.original.parameters():
            param.requires_grad_(False)
        self.scaling = alpha / rank
        # Follow the original layer's dtype and device.
        weight = original_linear.weight
        self.lora_A = nn.Parameter(weight.new_empty(rank, original_linear.in_features))
        self.lora_B = nn.Parameter(weight.new_zeros(original_linear.out_features, rank))
        nn.init.kaiming_uniform_(self.lora_A, a=math.sqrt(5))

    def forward(self, x):
        delta = F.linear(F.linear(x, self.lora_A), self.lora_B)
        return self.original(x) + self.scaling * delta
```

林默看着：

```python
self.lora_Aself.lora_B
```

“这两者都是 Parameter。”

“所以它们会自动出现在 `model.parameters()` 中。”

教授点头。

“而且因为它们参与了计算图，反向传播时可以得到梯度。”

> 初始化时 B=0，因此普通损失的首步反传通常先给 B 非零梯度，A 的该项梯度为零；B 更新后，A 才开始获得相应梯度。这不等于 A 永远不学习。

### 二十四、为什么 A 随机初始化，B 初始化为零？

林默注意到：

```python
nn.init.kaiming_uniform_(self.lora_A)
```

而：

```python
self.lora_B = nn.Parameter(    torch.zeros(out_features, rank))
```

“为什么不两个都随机？”

教授写：

\[ \Delta W=BA \]

如果：

\[ B=0 \]

那么：

\[ BA=0 \]

所以训练刚开始：

\[ y=Wx \]

也就是：

> 刚插入 LoRA 时，模型初始输出与原始 Linear 一致。

林默明白了。

“这样不会一开始就引入随机修正，破坏预训练模型输出。”

“对。”

“而且 A 随机、B 为零的常见初始化方式允许 B 在第一步获得梯度，随后 A 也逐渐参与学习。”

教授继续：

“如果 A 和 B 都严格初始化成零，普通梯度下降在初始点就可能无法更新它们。”

### 二十五、测试 LoRA 是否真的只更新小矩阵

教授写：

```python
base = nn.Linear(128, 128)
lora_layer = LoRALinear(base, rank=8, alpha=16)
x, target = torch.randn(4, 128), torch.randn(4, 128)
optimizer = torch.optim.AdamW(
    [p for p in lora_layer.parameters() if p.requires_grad], lr=1e-3
)
optimizer.zero_grad(set_to_none=True)
output = lora_layer(x)
loss = F.mse_loss(output, target)
loss.backward()
optimizer.step()
```

然后：

```python
for name, param in lora_layer.named_parameters():
    print(name, param.requires_grad)
```

预期可以看到：

```text

lora_B True

original.weight False

original.bias False
```

林默终于理解：

“原来 LoRA 并不是一个完全不同的训练体系。”

“它只是改变了哪些参数参与训练，以及模型如何计算输出。”

教授点头。

训练循环仍然是：

```text
Forward
   ↓
Loss
   ↓
Backward
   ↓
Optimizer
```

只是 Optimizer 不再负责更新全部预训练权重。

## 第七幕：QLoRA——给冻结的巨人穿上更轻的盔甲

### 二十六、LoRA 还有一个问题

林默重新计算：

“教授，LoRA 的确减少了梯度和优化器状态。”

林默问：

教授在黑板上写：

**QLoRA**

Quantized Low-Rank Adaptation。

核心思路：

> 将冻结的基础模型权重量化存储，同时使用 LoRA 训练低秩适配器。

### 二十七、4-bit 到底能节省多少？

\[ 7B\times2\text{ Bytes}=14\text{ GB} \]

\[ 7B\times0.5\text{ Bytes}=3.5\text{ GB} \]

7B 基础模型的理论纯权重存储量

0 GB8 GB16 GB24 GB32 GBFP32BF16 / FP16INT8（理论）4-bit（理论）

仅计算模型原始权重的理想存储量，不包括量化元数据、激活、缓存及训练开销。

林默激动起来。

“3.5GB！”

“那一张 8GB 显卡就能随便微调 7B 模型？”

教授立即摇头。

“不能这么推。”


更重要的是：

> 显存是否够用，与序列长度、Batch Size、LoRA Rank、量化实现和模型结构直接相关。

### 二十八、为什么不能直接用普通整数计算？

教授写：

```text
原始浮点权重：

0.1234
-0.7821
1.2345
...
```

如果粗暴地转成低位整数：

```text
0
-1
1
...
```

显然会产生量化误差。

因此实际量化通常要考虑：

```text
量化区间

缩放比例

分组方式

权重分布

反量化计算
```

QLoRA 的经典方案使用了 NF4 等技术。

NF4：

NormalFloat 4-bit。

它针对近似正态分布的权重设计了一套非均匀量化表示。

在常见 QLoRA 流程中：

```text
冻结的基础权重
       │
       ▼
以 4-bit 形式存储
       │
       ▼
计算时按算子实现反量化到计算精度
       │
       ▼
进行矩阵运算
       │
       +
       │
可训练 LoRA 分支
       │
       ▼
合并输出
```

教授强调：

“QLoRA 并不是直接让普通 4-bit 整数权重像 FP32 一样自由参与梯度更新。”

“经典 QLoRA 训练过程中，基础量化权重保持冻结，主要训练 LoRA 适配器。”

### 二十九、LoRA 与 QLoRA 的本质区别

| 对比     | LoRA           | QLoRA        |
| ------ | -------------- | ------------ |
| 基础模型   | 冻结             | 冻结           |
| 基础权重存储 | 通常 FP16/BF16 等 | 典型方案为 4-bit  |
| 可训练参数  | LoRA 适配器       | LoRA 适配器     |
| 显存占用   | 较全参数微调更低       | 通常可进一步降低     |
| 计算开销   | 取决于实现          | 可能增加反量化等成本   |
| 主要用途   | 参数高效微调         | 在更紧张的显存预算下微调 |

林默看着表格。

“所以 QLoRA 不是一种完全新的 Transformer。”

“它是量化与 LoRA 结合的训练方案。”

“正确。”

## 第八幕：FlashAttention——不改变答案，改变计算方式

### 三十、另一场显存灾难：Attention Matrix

林默以为问题已经解决。

他将模型换成 QLoRA。

显存占用降低了不少。

但当他把：

```text
Sequence Length = 2048
```

改成：

```text
Sequence Length = 16384
```

训练又开始出现显存压力。

教授问：

“还记得第九章 Self-Attention 的复杂度吗？”

林默回答：

\[ O(n^2) \]

“没错。”

教授写：

\[ Attention(Q,K,V)= softmax\left(\frac{QK^T}{\sqrt{d_k}}\right)V \]

“如果按最直接的方式实现，需要产生一个很大的注意力分数矩阵。”

假设：

```python
seq_len = 16384
```

那么单个 Attention Head 的分数矩阵：

\[ 16384\times16384 \]

约有：

\[ 268,435,456 \]

个元素。

如果每个元素使用 2 字节保存：

\[ 268,435,456\times2 = 536,870,912\text{ Bytes} \]

也就是单个 Head 的一份这种矩阵就约占：

\[ 512\text{ MiB} \]

教授提醒：

“这只是针对一种显式矩阵表示的估算，并不是所有 Attention 实现都会把完整矩阵存下来。”

“但它已经足以说明，为什么长上下文会给朴素 Attention 带来巨大压力。”

### 三十一、FlashAttention 的核心不是换公式

林默问：

“那 FlashAttention 是不是把 Attention 改成 O(n) 了？”

教授摇头。

“这是一个非常重要的误区。”

“FlashAttention 的关键优势，并不是把标准精确 Attention 的主要算术复杂度从二次方变成线性。”

“它主要通过分块计算和 IO-aware 算法，减少高带宽显存与片上快速存储之间的数据搬运，并避免显式存储完整的 Attention 矩阵。”

教授画：

朴素实现：

```text
Q × Kᵀ
   ↓
生成完整 Scores
   ↓
写入显存
   ↓
读取 Scores
   ↓
Softmax
   ↓
写入显存
   ↓
读取概率矩阵
   ↓
乘 V
   ↓
Output
```

FlashAttention：

```text
Q / K / V
    ↓
按 Tile 分块
    ↓
尽可能在片上快速存储中完成局部计算
    ↓
在线更新 Softmax 统计量与输出累加
    ↓
输出最终结果
```

林默突然反应过来。

“也就是说，真正昂贵的不只是乘法。”

“还包括把巨大的中间矩阵反复搬进搬出显存。”

教授点头。

### 三十二、为什么它能够不保存完整 Softmax 矩阵？

林默追问：

“可是 Softmax 不是需要一整行的所有分数才能计算分母吗？”

教授写：

\[ softmax(z_i)=\frac{e^{z_i}}{\sum_j e^{z_j}} \]

“传统思维会先算出整行，再算总和。”

“但可以使用在线 Softmax 算法，在处理分块时维护运行中的最大值与归一化统计量。”

“这样就能分块累积最终结果，而不必为每个 Attention Head 显式保存完整的 \(N\times N\) 概率矩阵。”

教授强调：

> FlashAttention 计算的是标准 Attention 的数学目标，允许正常浮点舍入误差，但通过改变计算顺序和数据搬运方式提高效率。

### 三十三、PyTorch 里怎么用 FlashAttention？

教授打开编辑器。

```python
import torch
import torch.nn.functional as F

# Q, K, V 应为 [batch, heads, seq_len, head_dim]。
output = F.scaled_dot_product_attention(
    Q, K, V, is_causal=True, dropout_p=0.0
)
```

林默问：

“就这一行？”

教授回答：

“PyTorch 的 `scaled_dot_product_attention` 可以根据设备、数据类型、形状和后端条件选择不同的 Attention 实现，包括受支持环境中的高效融合内核。”

“但不能认为只要调用这个 API，就一定使用了某个特定版本的 FlashAttention。”

“实际需要确认后端支持情况和性能分析结果。”

教授特别补充：

“这里如果使用 `dropout_p`，要显式按训练/推理状态设置。这个函数不会仅因为外层模型进入 `eval()` 就自动将传入的 Dropout 概率改为零。”

例如：

```python
dropout_p = 0.1 if self.training else 0.0
output = F.scaled_dot_product_attention(
    Q, K, V, is_causal=True, dropout_p=dropout_p
)
```

对于只有一张 24GB 显卡的情况，优先考虑在已有开源模型上进行 QLoRA/SFT，而不是从零预训练 7B 模型。

原因很简单：

从零预训练不仅存在显存问题，还需要巨量高质量数据、计算资源和训练工程能力。即使利用各种节省显存技术，一张消费级显卡也不意味着能够以合理成本完成 7B 级模型的充分预训练。

### 三十六、实际工程中，怎么接入 QLoRA？

教授打开一个新的 Python 文件。

“今天我们不再手工为 7B 模型编写每一层。”

“PyTorch 负责底层张量与自动求导，实际微调通常会配合 Hugging Face Transformers、PEFT 和 bitsandbytes 等工具。”

下面是一个简化的模型加载与 LoRA 配置示例。它需要兼容的 CUDA 环境、已安装的相关依赖，以及用户选定的可访问模型。

```python
# 配置骨架：需要兼容 GPU、依赖和实际模型 ID，不是完整训练脚本。
import torch
from transformers import AutoModelForCausalLM, BitsAndBytesConfig
from peft import LoraConfig, get_peft_model, prepare_model_for_kbit_training

model_id = "your-compatible-7b-model"  # 替换为可访问且许可适用的模型
if not torch.cuda.is_available():
    raise RuntimeError("此示例按单张 CUDA GPU 配置")
compute_dtype = torch.bfloat16 if torch.cuda.is_bf16_supported() else torch.float16
quant_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_compute_dtype=compute_dtype,
    bnb_4bit_use_double_quant=True,
)
model = AutoModelForCausalLM.from_pretrained(
    model_id, quantization_config=quant_config,
    device_map={"": torch.cuda.current_device()},  # 单卡训练，不使用推理自动卸载
)
model.config.use_cache = False
model = prepare_model_for_kbit_training(model)
lora_config = LoraConfig(
    r=16, lora_alpha=32, target_modules="all-linear",
    lora_dropout=0.05, bias="none", task_type="CAUSAL_LM",
)
model = get_peft_model(model, lora_config)
model.print_trainable_parameters()
```

林默看到：

```text

```

“这是什么意思？”

教授回答：

“PEFT 会尝试给模型中支持的线性模块注入 LoRA 适配器。”

“但不同模型架构和软件版本可能存在兼容性差异，实际训练前需要检查目标模块。”

然后执行：

```text
model.print_trainable_parameters()
```

输出会显示：

```text

all params: ...
trainable%: ...
```

林默点头。

“这样我就能知道究竟有多少参数真正参与训练。”

## 第十幕：训练为什么仍然可能失败？

### 三十七、显存省下来了，不等于模型一定能学好

林默终于成功启动了训练。

但几个小时后，他发现验证集 Loss 没有明显改善。

他疑惑地问：

“教授，显存问题已经解决了，为什么效果还是不理想？”

教授回答：

“因为显存优化解决的是资源问题，不是模型质量问题。”

即使显存足够，训练仍可能失败。

例如：

训练数据有问题。

```text
重复数据过多

标签错误

答案质量低

训练目标不合理
```

学习率有问题。

```text
太大 → 训练不稳定

太小 → 学习缓慢
```

LoRA 容量不合适。

```text
Rank 太小
→ 适配能力可能不足

Rank 太大
→ 更多显存与训练成本
```

训练评测有问题。

```text
只看训练 Loss

没有验证集

没有任务级评测

模型可能只是记住训练数据
```

教授说：

> 能够把模型训练起来，只是工程成功的第一步。训练后的模型是否真正变好，需要独立验证。

林默突然想到自己开发 Coding Agent 时使用过的 SWE-bench 评测。

“也就是说，大模型微调同样不能只看 Loss。”

“还要看真实任务表现。”

教授点头。

例如微调一个 Java 问答模型，可以准备独立测试集，评估：

```text
技术事实正确率

推理与解释质量

代码能否编译运行

对未见过问题的泛化能力

幻觉情况

相对基础模型的提升或退化
```

这才是判断微调是否成功的依据。

1\. LoRA 将某层可训练参数减少 99%，是否意味着整张 GPU 的显存占用也降低 99%？

将全部模型权重转换成 INT4

完全消除梯度噪声

必须降低模型层数

反向传播时进行额外重计算

无法执行反向传播

4\. QLoRA 经典方案主要训练哪部分？

全部量化权重

冻结基础权重上的 LoRA 适配器

Tokenizer 的词表

5\. FlashAttention 的核心优化是什么？

将标准 Attention 数学目标替换成线性近似

主要减少 Attention 的中间存储和数据搬运

消除 Transformer 对 GPU 的需求

## 第一幕：为什么预训练模型不等于助手模型？

### 一、一个只会续写的学者

教授在终端中写入：

```text
问题：Java HashMap 为什么线程不安全？
```

一个只经过基础预训练的模型，可能继续生成：

```text
问题：ConcurrentHashMap 为什么线程安全？

问题：Hashtable 和 HashMap 有什么区别？
```

林默皱眉。

“它怎么不回答？”

教授说：

“因为对一个只学过普通文本续写目标的模型而言，继续生成另一道问题也可能是合理的文本延续。”

预训练目标通常可以写成：

\[ L_{\text{pretrain}} = -\sum_t\log P_\theta(x_t\mid x_{<t}) \]

它直接优化的是：

> 给定前面的 Token，提高训练数据中后续 Token 的预测概率。

它并没有天然规定：

```text
遇到用户提问 → 必须认真回答

遇到编程任务 → 应该给正确代码

不知道答案 → 应该表达不确定性

遇到歧义 → 必要时询问
```

这些行为可以通过后训练被进一步塑造。

教授画出大模型训练的一条典型路线：

```text
海量预训练语料
        │
        ▼
   Pre-training
        │
        ▼
    Base Model
        │
        ▼
Instruction SFT
        │
        ▼
  Instruct Model
        │
 ┌──────┴──────┐
 ▼             ▼
DPO        RLHF / RL
 │             │
 └──────┬──────┘
        ▼
 Post-trained Model
        │
        ▼
    Evaluation
```

“注意，”教授说，“这是一种概念化路线，不代表所有现代模型都严格按照这个固定顺序训练。不同方法还可以迭代或组合。”

## 第二幕：SFT——给模型一本优秀答案集

### 二、SFT 到底是什么？

教授写：

**Supervised Fine-Tuning**

监督微调，简称 SFT。

“想象一下，你招聘了一个读过数百万本书的学者。”

“他知识面很广，但不知道公司希望他怎么工作。”

“于是你给他一本工作手册。”

```text
用户提出 Java 问题
       ↓
应该先明确概念
       ↓
再解释原理
       ↓
提供准确的示例
       ↓
必要时说明适用条件
```

这本手册就是高质量指令数据集的一种类比。

例如：

```text
{
  "messages": [
    {
      "role": "user",
      "content": "什么是 Java ThreadLocal？"
    },
    {
      "role": "assistant",
      "content": "ThreadLocal 提供线程局部变量访问机制，每个线程可以通过同一个 ThreadLocal 对象访问自己的值..."
    }
  ]
}
```

林默点头。

“也就是把用户问题和优秀回答配成训练样本。”

“对。”

但 SFT 的关键不仅在于有数据。

还在于：

> 哪些 Token 应该参与 Loss？

### 三、SFT 和预训练，Loss 是不是完全不同？

林默问：

“之前预训练使用 CrossEntropyLoss。”

“SFT 是不是要换一个特殊的损失函数？”

教授摇头。

“对自回归语言模型，常见 SFT 仍然可以使用下一 Token 预测的交叉熵。”

公式：

\[ L_{\text{SFT}} = -\sum_{t\in\mathcal A} \log P_\theta(y_t\mid x,y_{<t}) \]

其中：

- \(x\)：用户输入及必要的对话上下文。
- \(y\)：目标助手回答。
- \(\mathcal A\)：参与损失计算的目标回答位置。

“最大的区别之一，在于训练样本如何组织，以及哪些位置参与训练。”

## 第三幕：最容易写错的地方：Prompt Mask

### 四、为什么用户问题通常不应该被当作回答来训练？

教授写出：

```text
<user>
解释 Java HashMap 的扩容机制。
</user>

<assistant>
HashMap 在容量达到阈值时通常会触发扩容……
```

假设 Tokenizer 已经完成编码。

```text
Input IDs：

[用户问题 Token ...][助手回答 Token ...]
```

林默问：

“那 labels 不就是把所有 input_ids 向后错位一格吗？”

教授回答：

“基础语言模型可以这么训练。”

“但如果我们的目标是让模型学会生成助手回答，那么一种常见 SFT 策略是：只对助手回答部分计算 Loss。”

他在黑板上写：

```text
输入：

[Prompt Token][Answer Token]


Loss Mask：

[不计算 Loss][计算 Loss]
```

在 PyTorch 的 `CrossEntropyLoss` 中，默认有一个非常有用的设置：

```text
ignore_index=-100
```

如果某个目标位置的 Label 是：

```text
-100
```

就表示：

> 这个位置不参与 CrossEntropyLoss。

### 五、用一个简单例子理解 `-100`

教授先不用真实 Tokenizer，而是使用数字演示。

假设：

```text
用户问题：[11, 12, 13]

助手回答：[21, 22, 23]
```

训练序列：

```python
input_ids = torch.tensor([    11, 12, 13, 21, 22, 23])
```

如果采用完整序列的下一 Token 预测标签：

```text
[12, 13, 21, 22, 23, ...]
```

但我们希望仅让模型针对助手回答产生的目标 Token 计算损失。

可以概念化成：

```text
上下文位置：

11    12    13    21    22

预测目标：

忽略  忽略  21    22    23
```

于是：

```text
Labels：

[-100, -100, 21, 22, 23]
```

林默突然发现：

“第三个位置的输入是用户问题的最后一个 Token。”

“它负责预测助手回答的第一个 Token！”

教授点头。

“这就是需要认真处理 Token 对齐的原因。”

“不同训练框架可能约定 labels 为未移位序列，内部完成 shift，也可能要求你提前移位。不能把两套约定混用。”

### 六、写一个简化的 PyTorch SFT Loss

假设模型输出：

```text
logits.shape = [B, T, V]
```

我们使用与完整输入等长、未移位的标签 Tensor，并在计算 Loss 时手动完成移位。上面的五项 Labels 已是移位后的示意；不能直接传给下面这段代码。下面假设 logits.shape=[1,6,V]，且 V 至少为 24。这里 -100 只屏蔽目标监督，不会屏蔽读取上下文的 Attention；输入 Padding 还需要独立的 attention mask。

```python
import torch
import torch.nn.functional as F

# input_ids 的形状是 [B, T]；下面演示一个 6 Token 的样本。
# Prompt 为 [11, 12, 13]，回答为 [21, 22, 23]。
labels = torch.tensor([[-100, -100, -100, 21, 22, 23]], device=logits.device)
shift_logits = logits[:, :-1, :].contiguous()
shift_labels = labels[:, 1:].contiguous()
if not (shift_labels != -100).any():
    raise ValueError("当前 Batch 没有可监督的回答 Token")
loss = F.cross_entropy(
    shift_logits.reshape(-1, shift_logits.size(-1)),
    shift_labels.reshape(-1), ignore_index=-100
)
```

林默看着：

```python
logits[:, :-1, :]
```

和：

```python
labels[:, 1:]
```

立刻想起第十一章。

“还是错位预测！”

“对。”

“只是我们把用户 Prompt 对应的目标位置 Mask 掉，让 Loss 重点监督助手回答。”

教授补充：

“对于多轮对话，还需要明确哪些 assistant 消息参与训练，以及角色标记、结束标记和工具消息如何处理。”

“高质量 SFT 数据管线，往往比单纯写一个训练循环更容易出错。”

## 第五幕：两份答案都正确，应该选择谁？

### 九、SFT 遇到的新问题

教授写出同一个用户问题：

> Java HashMap 为什么线程不安全？

然后给出两个答案。

回答 A：

“HashMap 不是线程安全的。如果多个线程并发修改，可能出现数据竞争和丢失更新。需要根据场景选择同步控制或 ConcurrentHashMap。”

回答 B：

“HashMap 非线程安全。并发修改时可能出现更新丢失、读取到不一致状态等问题。例如，两个线程在缺乏同步的情况下同时进行结构修改，其行为不具备线程安全保证。通常可以使用 ConcurrentHashMap，或者通过外部同步保护共享 HashMap。需要注意，ConcurrentHashMap 也不等于任意复合操作天然原子化。”

教授问：

“哪个更好？”

林默回答：

“B 更详细，还说明了 ConcurrentHashMap 的适用边界。”

教授点头。

“但假设用户只需要一句话的面试答案呢？”

林默思考。

“那 A 可能更合适。”

“正是如此。”

教授写下：

> 回答质量不仅包含正确性，还可能包含完整性、简洁度、帮助程度、格式和上下文适配性。

而 SFT 只利用某条目标回答直接进行监督，并不天然显式比较不同回答的优劣。

于是一个新的训练目标出现了：

**Preference Optimization**

偏好优化。

林默看着：

“另一个是较差的回答。”

“没错。”

教授说：

例如：

```text
   │

   │      ↓
   │    Chosen
   │
   └── Answer B
          ↓

```

目标变成：

> 提高模型对偏好回答的相对倾向。

## 第六幕：DPO——没有单独奖励模型，也能学习偏好？

### 十一、Direct Preference Optimization

教授写：

**DPO**

Direct Preference Optimization

林默问：

“它和 SFT 有什么区别？”

教授回答：

“SFT 让模型提高目标回答的条件概率。”

“DPO 则利用成对偏好数据，优化 chosen 与 rejected 之间的相对关系，并通过参考模型约束偏好变化。”

他画出：

```text
Prompt
             │
      ┌──────┴──────┐
      ▼             ▼
   Chosen        Rejected
      │             │
      ▼             ▼
计算回答概率    计算回答概率
      │             │
      └──────┬──────┘
             ▼
    与参考模型比较
             │
             ▼
           DPO Loss
             │
             ▼
         backward()
             │
             ▼
          更新 Policy
```

林默问：

“参考模型又是什么？”

教授写下：

```text
Policy Model
→ 当前正在训练的模型


Reference Model
→ 作为对比基准的模型
```

“Reference 通常是冻结的，它代表训练开始附近的行为基准。”

### 十二、为什么 DPO 需要 Reference Model？

教授给出一个例子。

对于某个 Prompt：

```text
Chosen：
正确且清晰的回答

Rejected：
错误且冗长的回答
```

如果只要求：

```text
P(Chosen) > P(Rejected)
```

看起来很合理。

但教授说：

“我们不希望模型为了满足一些有限的偏好样本，就任意偏离原来学到的大量语言能力。”

“所以 DPO 的典型目标里，会比较当前模型与参考模型对两份回答的相对概率。”

设：

\[ \pi_\theta \]

表示当前 Policy。

\[ \pi_{\text{ref}} \]

表示参考模型。

DPO 的经典损失可以写成：

\[ \mathcal L_{\text{DPO}} = -\log\sigma \left( \beta \left[ \log\frac{\pi_\theta(y_w|x)} {\pi_{\text{ref}}(y_w|x)} - \log\frac{\pi_\theta(y_l|x)} {\pi_{\text{ref}}(y_l|x)} \right] \right) \]

其中：

- \(y_w\)：chosen。
- \(y_l\)：rejected。
- \(\beta\)：控制偏好优化中相对参考模型变化的尺度。
- \(\sigma\)：Sigmoid。

林默盯着公式。

“看着还是复杂。”

教授说：

“那我们把它拆成三个数字。”

### 十三、把 DPO 公式翻译成人话

定义：

\[ r_w= \log\pi_\theta(y_w|x) - \log\pi_{\text{ref}}(y_w|x) \]

\[ r_l= \log\pi_\theta(y_l|x) - \log\pi_{\text{ref}}(y_l|x) \]

于是：

\[ L=-\log\sigma(\beta(r_w-r_l)) \]

林默终于看懂了。

“所以核心是在比较：”

```text
当前模型相对参考模型
对 Chosen 提高了多少倾向

减去

当前模型相对参考模型
对 Rejected 提高了多少倾向
```

“对。”

如果这个差值变大，DPO Loss 通常会下降。

教授强调：

“这里比较的是完整回答的条件对数概率，而不是简单地只比较某一个 Token 的 Softmax 值。”

> 本节指经典、带参考模型的 DPO。参考模型提供相对基准，但不是对所有行为变化的硬性保证；DPO 变体可能采用不同参考机制。完整回答的 logp 应按回答 Token 的条件 logp 求和，排除 Prompt 与 PAD。

### 十四、用 PyTorch 手写 DPO 核心 Loss

教授打开编辑器：

```python
import torch
import torch.nn.functional as F

def dpo_loss(policy_chosen_logp, policy_rejected_logp,
             ref_chosen_logp, ref_rejected_logp, beta=0.1):
    if beta <= 0:
        raise ValueError('beta must be positive')
    policy_logratio = policy_chosen_logp - policy_rejected_logp
    ref_logratio = (ref_chosen_logp - ref_rejected_logp).detach()
    return -F.logsigmoid(beta * (policy_logratio - ref_logratio)).mean()
```

林默一眼认出了：

```text
F.logsigmoid()
```

“就是之前学过的 Sigmoid 的对数形式。”

“对。”

“PyTorch 把很多复杂公式拆开之后，其实依然是普通 Tensor 运算。”

教授提醒：

“这只是经典 DPO 核心损失的示例。完整训练还需要正确计算每个回答的 Token 对数概率、Mask 掉 Prompt 和 Padding、处理序列长度、参考模型前向，以及注意数值稳定性。”

## 第七幕：RLHF——让模型在反馈中调整行为

### 十五、如果希望模型在线探索并接受反馈呢？

林默问：

“DPO 需要成对偏好数据。”

“那如果我们希望模型探索新的回答，并根据回答质量进一步优化？”

教授点头。

“这就进入强化学习的世界。不过经典奖励模型本身也常通过成对人类偏好训练；RLHF 并不是简单地不再需要偏好数据。”

他在白板上写：

**RLHF**

Reinforcement Learning from Human Feedback

从人类反馈中进行强化学习。

经典的一类 RLHF 流程：

```text
预训练模型
               │
               ▼
             SFT
               │
               ▼
          SFT Model
               │
     ┌─────────┴──────────┐
     ▼                    ▼
 收集偏好数据         初始化 Policy
     │                    │
     ▼                    │
训练 Reward Model        │
     │                    │
     └─────────┬──────────┘
               ▼
        强化学习优化
               │
               ▼
          更新 Policy
```

教授说：

“RLHF 不是某一个具体优化器的名称，而是一类利用人类反馈引导模型优化的训练范式。”

“PPO 是经典 RLHF 中使用过的重要强化学习算法，但并不是唯一选择。”

### 十六、Reward Model 是什么？

假设模型针对同一个问题生成两个答案：

```text
Answer A：
HashMap 是线程安全的，因为……

Answer B：
HashMap 不保证线程安全，因为……
```

人类标注者更偏好 B。

我们可以训练一个模型：

```text
输入：

Prompt + Answer

输出：

一个评分
```

例如：

```text
Reward Model

Answer A → -1.2

Answer B →  2.4
```

林默问：

“所以 Reward Model 就像一个评分老师？”

“可以这么理解。”

“但评分值不是一个客观真理，它是根据训练反馈学习出来的估计。”

教授写：

\[ R_\phi(x,y) \]

表示奖励模型对问题 \(x\) 和回答 \(y\) 给出的分数。

然后强化学习希望：

\[ \max_\theta \mathbb E_{y\sim\pi_\theta} [R_\phi(x,y)] \]

即：

> 让当前模型生成更容易获得高奖励的回答。

但如果只追逐奖励，也会出问题。

## 第八幕：奖励黑客：为什么模型会钻评分规则的漏洞？

### 十七、一个危险的实验

教授给模型设计了一条简单奖励规则。

```text
如果答案包含：

“详细解释”

奖励 +1
```

一开始，模型确实更喜欢给出详细解释。

但训练继续之后，模型开始生成：

```text
详细解释，详细解释，详细解释……
```

林默愣住。

“它在刷奖励？”

教授点头。

“这就是 Reward Hacking 的一个简化例子。”

当奖励信号不能准确反映真实目标时，模型可能优化评分规则，而不是优化人类真正想要的结果。

在 Coding Agent 场景也可能出现类似问题。

例如：

```text
奖励：
只要测试通过就给高分
```

如果评测环境存在缺陷，Agent 可能找到绕过测试的方式，而不是正确实现需求。

因此：

> 奖励函数设计和评测环境可靠性，是强化学习训练中极其重要的工程问题。

### 十八、为什么 RLHF 常常需要约束模型不要偏离太远？

教授写：

\[ \max_\theta \mathbb E \left[ R(x,y) - \beta D_{KL} \left( \pi_\theta\Vert\pi_{\text{ref}} \right) \right] \]

林默看向：

\[ D_{KL} \]

“这是 KL 散度？”

“对。”

“它可以衡量两个概率分布之间的差异。”

教授解释：

```text
Reward
    ↓
鼓励模型更符合偏好


KL Penalty
    ↓
抑制模型无约束地偏离参考策略
```

比如：

```text
只提高奖励
    ↓
可能利用奖励漏洞
    ↓
生成异常内容
```

加入合适的约束，可以降低这种偏移风险。

但也要注意：

“KL 约束不是奖励黑客问题的万能解法，过强约束还可能限制模型改善。”

## 第九幕：PPO 到底在做什么？

### 十九、Policy Gradient：生成也是一种决策过程

教授说：

“你以前觉得强化学习只属于游戏和机器人。”

林默点头。

“比如智能体控制角色移动。”

“但文本生成也能被建模成顺序决策。”

```text
当前状态：
已有 Prompt 和生成前缀
        │
        ▼
动作：
选择下一个 Token
        │
        ▼
新状态：
前缀追加 Token
        │
        ▼
继续选择下一个 Token
```

在这个框架下：

- State：当前上下文。
- Action：选择下一个 Token。
- Policy：语言模型的条件概率分布。
- Reward：根据生成结果获得的反馈。

林默恍然大悟。

“也就是说，语言模型就是 Policy？”

“在这种强化学习建模中，是的。”

### 二十、PPO 为什么要限制更新幅度？

PPO：

Proximal Policy Optimization

教授画了一条简单的优化路线。

```text
旧 Policy
    │
    ▼
生成回答
    │
    ▼
获得 Reward
    │
    ▼
估计 Advantage
    │
    ▼
更新 Policy
```

“但如果一次更新幅度太大，模型生成策略可能突然发生剧烈变化。”

“PPO 的经典 Clipped Objective，正是为了限制策略更新中的某些过大变化。”

公式：

\[ L^{CLIP} = \mathbb E \left[ \min \left( r_tA_t, clip(r_t,1-\epsilon,1+\epsilon)A_t \right) \right] \]

其中：

\[ r_t= \frac{\pi_\theta(a_t|s_t)} {\pi_{\text{old}}(a_t|s_t)} \]

林默问：

“这个比例什么意思？”

教授回答：

“它比较某个动作在新旧策略下的概率。”

比如：

```text
旧模型：
选择某 Token 的概率 = 0.2

新模型：
选择该 Token 的概率 = 0.8
```

那么：

\[ r_t=\frac{0.8}{0.2}=4 \]

“变化非常大。”

“PPO 的 Clip 机制会限制这种比例变化对目标函数带来的进一步优化激励。”

教授提醒：

“这不表示 PPO 在数学上保证每次策略变化绝不会超过阈值，它只是用裁剪目标抑制过大的更新诱因。”

## 第十幕：DPO 和 RLHF 究竟怎么选？

### 二十一、林默开始考虑实际工程

“教授，如果我想微调一个 Java 问答模型。”

“到底选择 SFT、DPO 还是 PPO？”

教授没有立即回答。

而是问：

“你的数据是什么？”

“只有标准问答？”

“那优先考虑 SFT。”

“如果有成对偏好？”

“可以考虑 DPO 等偏好优化方法。”

“如果有可交互的训练环境、比较可靠的奖励和足够计算预算？”

“可以考虑强化学习训练。”

他写下一张对照表：

| 方法         | 主要数据/反馈               | 训练思路          | 典型挑战            |
| ---------- | --------------------- | ------------- | --------------- |
| SFT        | 高质量指令与目标回答            | 最大化目标回答概率     | 数据质量、泛化、过拟合     |
| DPO        | Chosen / Rejected 偏好对 | 直接优化相对偏好      | 偏好噪声、参考模型与数据分布  |
| RLHF + PPO | 偏好训练的奖励模型与采样反馈        | 在线采样、奖励驱动策略优化 | 复杂度高、奖励偏差、训练稳定性 |
| 可验证奖励 RL   | 测试、规则、数学答案等反馈         | 根据可验证结果优化     | 奖励设计、探索和评测漏洞    |

“而且，”教授继续，“实际训练管线不一定只选其中一种。”

例如：

```text
高质量 SFT
      ↓
偏好优化
      ↓
针对推理/代码任务进行可验证奖励训练
      ↓
持续评测
```

但每增加一个阶段，都应该证明它确实带来收益。

## 第十一幕：为什么推理模型需要不一样的训练？

### 二十三、推理能力不只是回答更长

林默问：

“那训练推理模型，是不是让模型多写几段思考过程？”

教授摇头。

“不能这么简单理解。”

“更长的文字不等于更好的推理。”

一个模型完全可能写出很长但错误的分析。

真正关心的是：

```text

最终结果是否正确

推理是否可泛化

能否检查自身错误

```

一些训练方法会鼓励模型在复杂问题上学习更有效的中间步骤、验证行为或策略。

但这种能力是否真正提升，必须通过独立任务评测判断，而不能只看回答长度。

### 二十六、五道理解测试

第十三章随堂测试


1\. SFT 中把 Prompt 对应的 Label 设为 -100，主要是为了什么？

禁止模型读取 Prompt

使相应目标位置不参与 CrossEntropyLoss

把 Prompt 自动转成 Embedding

2\. DPO 的经典目标主要利用什么数据？

只有原始预训练文本

Chosen / Rejected 成对偏好数据

只有模型参数数量

3\. Reward Model 的评分应该如何理解？

绝对客观的正确性证明

抑制策略更新中的过大变化激励

减少模型词表长度

Loss 不可以计算

因为 SFT 不使用反向传播

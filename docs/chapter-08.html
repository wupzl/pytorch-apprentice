第八天。

林默刚进实验室，就看到黑板上写着一句话：

今天天气不错。

教授问：

“把这句话喂给神经网络。”

林默愣了一下。

“直接这样？”

model("今天天气不错")

教授摇头。

“神经网络不会读中文。”

“它只认数字。”

于是，今天真正的问题出现了：

文字，怎么变成数字？

一、神经网络只认识数值

前面我们训练模型时，输入都是：

x = torch.tensor([
    [1.2, 3.4],
    [2.1, 5.7]
])

本质都是数字。

可文本是：

我喜欢 PyTorch

神经网络不能直接对字符做矩阵乘法：

W×“我” W \times \text{“我”}

没有意义。

所以必须先做转换：

文字
 ↓
数字
 ↓
Tensor
 ↓
神经网络

教授在黑板上写下第一个词：

Token

二、Token 到底是什么

林默问：

“Token 就是一个字吗？”

“有时候是，有时候不是。”

Token 可以是：

一个字
一个词
一个词的一部分
标点
特殊符号

比如一句英文：

I love PyTorch

一种最简单的切法：

["I", "love", "PyTorch"]

三个 Token。

中文：

我喜欢PyTorch

可能切成：

["我", "喜欢", "PyTorch"]

也可能：

["我", "喜", "欢", "Py", "Torch"]

不同 tokenizer 规则不同。

三、为什么不能直接“一个词一个 Token”

林默说：

“那按照词切不就行了吗？”

教授写：

北京
上海
程序员
神经网络
大模型
反向传播

看起来没问题。

但语言中的词太多了。

比如：

ChatGPT
ChatGPT-6
PyTorch
PyTorch2
foobar123
某个新出现的名字

如果每个完整词都必须提前放进词表，那么：

新词怎么办？

词表会无限膨胀。

所以现代大模型常用的是：

Subword Tokenization——子词切分。

也就是：

unbelievable

可能拆成：

un
believ
able

这样模型不需要记住世界上所有完整单词。

四、Tokenizer 的两个核心工作

教授写：

文本
 ↓
Tokenizer
 ↓
Token
 ↓
Token ID

Tokenizer 主要干两件事。

第一：

把文本切成 Token。

第二：

给每个 Token 一个整数编号。

例如词表：

0  <pad>
1  <unk>
2  我
3  喜欢
4  PyTorch
5  Java

那么：

我 喜欢 PyTorch

就变成：

[2, 3, 4]

于是 PyTorch 终于能处理：

token_ids = torch.tensor([2, 3, 4])

林默点头。

“所以 Token ID 就是 Token 的编号。”

“对。”

但教授马上补充：

Token ID 本身没有语义。

五、为什么 Token ID 不能直接输入神经网络

假设：

猫 = 10
狗 = 11
飞机 = 100

如果直接把 ID 当数值：

猫 = 10
狗 = 11
飞机 = 100

模型可能误以为：

狗比猫大 1
飞机比猫大 90

但这个数字差没有语义。

Token ID 只是数据库主键一样的东西。

就像：

user_id = 10001
user_id = 10002

不能说明第二个人比第一个人大一点。

所以需要下一步。

六、Embedding 登场

教授写：

embedding = nn.Embedding(
    num_embeddings=10000,
    embedding_dim=128
)

林默看着这个 API。

“这是什么？”

教授说：

“它可以理解成一张巨大的向量表。”

假设词表只有 5 个 Token，每个 Token 用 3 维向量表示：

Token 0 → [ 0.2, -0.1,  0.7]
Token 1 → [-0.4,  0.9,  0.3]
Token 2 → [ 0.8,  0.1, -0.2]
Token 3 → [ 0.5, -0.7,  0.6]
Token 4 → [-0.2,  0.4,  0.9]

这张表就是：

Embedding Matrix Embedding\ Matrix

形状：

[vocab_size, embedding_dim]

七、nn.Embedding 本质上就是查表

假设：

embedding = nn.Embedding(10000, 128)

内部参数形状：

[10000, 128]

也就是说：

10000 个 Token
每个 Token 128 维

输入：

token_ids = torch.tensor([2, 5, 9])

执行：

x = embedding(token_ids)

得到：

shape = [3, 128]

本质上就是：

取第2行
取第5行
取第9行

所以 Embedding 可以粗略理解成：

用 Token ID 去查对应向量。

八、那这些向量是谁定的？

林默问：

“难道人工规定？”

教授摇头。

“最重要的地方来了。”

这些 Embedding：

也是模型参数。

也就是：

embedding.weight

本身就是：

Parameter

训练开始时可能随机：

猫 → [0.12, -0.54, 0.33, ...]
狗 → [-0.72, 0.19, 0.05, ...]

然后通过：

Loss
 ↓
backward
 ↓
optimizer.step()

不断调整。

所以：

词向量不是人写进去的，而是训练出来的。

九、语义为什么会出现在向量里

教授写两句话：

我养了一只猫。

我养了一只狗。

在大量语料中：

猫
狗

经常出现在相似上下文。

比如：

喂__
抱__
宠物__
可爱的__

那么为了完成语言预测任务，模型会逐渐学到：

猫和狗在很多语境中有相似功能。

于是它们的向量可能越来越接近。

比如：

猫 → [0.7, 0.3, -0.2, ...]
狗 → [0.68, 0.29, -0.18, ...]

而：

数据库

可能离得很远。

这就是：

语义进入向量空间。

十、向量距离开始有意义了

假设二维世界：

          猫 ●
              狗 ●


数据库 ●


                         飞机 ●

猫和狗距离近：

相似

数据库较远：

不太相似

于是可以用：

Cosine Similarity

等指标衡量语义相似程度。

林默突然反应过来。

“这不就是我做 RAG 的向量检索？”

教授点头。

十一、RAG 的 Embedding 和 LLM 的 Token Embedding 是一回事吗？

这是一个非常容易混淆的问题。

教授写：

LLM 内部 Token Embedding

和：

RAG 文本 Embedding

它们都叫 Embedding。

但用途不同。

LLM 的 Token Embedding

输入：

Token ID

输出：

一个 Token 的向量

比如：

[batch, seq_len]

经过：

nn.Embedding(...)

得到：

[batch, seq_len, hidden_dim]

它是：

Transformer 内部表示的起点。

RAG Embedding

输入通常是：

一句话
一个段落
一个 chunk

输出：

一个整体语义向量

例如：

“Redis 为什么快？”
 ↓
[0.123, -0.312, ..., 0.88]

然后存进：

pgvector
Milvus
FAISS

做相似度检索。

所以：

Token Embedding
→ token 级


RAG Embedding
→ 文本片段级

虽然背后可能都用神经网络产生向量，但不能简单当成同一个东西。

十二、Embedding 为什么不是 One-Hot

教授又画出旧时代的方法。

假设词表：

猫
狗
鸟
车

One-Hot：

猫 = [1,0,0,0]
狗 = [0,1,0,0]
鸟 = [0,0,1,0]
车 = [0,0,0,1]

问题来了。

猫和狗：

距离？

猫和车：

距离？

从这种表示本身看：

都一样远。

One-Hot 不携带语义相似性。

而 Embedding：

猫 = [0.81, 0.23, -0.11]
狗 = [0.79, 0.25, -0.09]
车 = [-0.42, 0.61, 0.77]

猫狗就可以自然靠近。

十三、Embedding 其实是降维

假设词表：

50000

One-Hot 每个词：

50000 维

但 Embedding 可以：

768 维

所以：

50000维稀疏表示
 ↓
768维稠密表示

而且这 768 维是：

可学习的分布式表示。

这也是深度学习非常关键的思想。

教授写：

import torch
import torch.nn as nn

embedding = nn.Embedding(

    embedding_dim=4
)

tokens = torch.tensor([
    2, 5, 7
])

x = embedding(tokens)

print(x.shape)

输出：

torch.Size([3, 4])

为什么？

3 个 Token
×
每个 Token 4 维

所以：

[3,4]

十五、如果有 Batch 呢？

输入：

tokens = torch.tensor([
    [2, 5, 7],
    [1, 3, 9]
])

shape：

[2,3]

意思：

2 个样本
每个样本 3 个 Token

经过：

x = embedding(tokens)

得到：

[2,3,4]

也就是：

batch_size = 2
seq_len = 3
embedding_dim = 4

这组 shape 极其重要。

因为进入 Transformer 后，你会天天看到：

[batch_size, seq_len, hidden_size]

十六、序列长度 Seq Len 出现了

一句话：

我 喜欢 PyTorch

三个 Token：

seq_len = 3

另一句话：

我 非常 喜欢 使用 PyTorch 训练 模型

可能 7 个 Token：

seq_len = 7

但是一个 Batch 需要组织成 Tensor：

[batch_size, seq_len]

问题来了。

不同句子长度不一样怎么办？

教授写：

Padding

十七、Padding：把队伍补齐

句子 A：

我 喜欢 PyTorch

3 Token。

句子 B：

我 学习

2 Token。

如果词表定义：

<PAD> = 0

那么：

A：
[我, 喜欢, PyTorch]

B：
[我, 学习, PAD]

于是长度统一：

3

形成：

[batch_size, seq_len]

十八、但 PAD 不能让模型当正常词处理

林默马上发现：

“那模型不会以为 PAD 也是内容吗？”

“所以需要 Mask。”

比如：

Token IDs:
[12, 35, 98, 0, 0]

对应：

Attention Mask:
[1, 1, 1, 0, 0]

意思：

1 → 真正 Token
0 → Padding

以后 Attention 计算时：

不应该让 PAD 影响正常内容。

这就是：

attention_mask

的一个重要来源。

十九、特殊 Token

教授又写：

[CLS]
[SEP]
[BOS]
[EOS]
[PAD]
[UNK]

不同模型会有不同特殊 Token。

常见含义：

BOS
→ Begin Of Sequence

→ 补齐

例如：

模型不仅看到内容。

还知道：

在哪里结束

二十、Embedding 有一个致命问题

教授突然写：

我 喜欢 狗

经过 Tokenizer：

[12, 35, 91]

经过 Embedding：

[
  vector(我),
  vector(喜欢),
  vector(狗)
]

林默点头。

教授又写：

狗 喜欢 我

Tokenizer：

[91, 35, 12]

Embedding：

还是：

vector(狗)
vector(喜欢)
vector(我)

教授问：

“单看每个 Token 的 Embedding，模型知道谁在第一位吗？”

林默停住了。

“Embedding 自己不知道位置。”

“对。”

nn.Embedding 只告诉模型“这是什么 Token”。

却没有告诉模型：

“它在第几个位置。”

于是又出现了一个新问题：

Position

二十一、词序非常重要

这两句话：

和：

Token 基本一样。

但顺序不同，意义完全不同。

所以：

Token Embedding

还不够。

需要加入：

形成：

Token Embedding
+

例如：

=
“我”的语义向量
+
“第1个位置”的向量

喜欢
=
“喜欢”的语义向量
+
“第2个位置”的向量

PyTorch
=
“PyTorch”的语义向量
+
“第3个位置”的向量

二十二、这就是 Transformer 的入口

教授终于画出：

文本
 ↓

 ↓

 ↓
Embedding
 ↓

 ↓

 ↓

林默看着这张图。

突然发现：

前七章所有东西都没有白学。

因为这里仍然是：

Tensor
Parameter
Module
Forward
Loss
Backward

只不过输入从：

普通数值

变成了：

Token

二十三、“国王 - 男人 + 女人 = 女王”到底是真的吗？

林默突然想起经典例子：

king - man + woman ≈ queen

教授说：

“这是早期词向量模型里一个非常经典的现象，但不要把它理解成所有现代 Embedding 都严格满足这种算术。”

核心想表达的是：

向量空间可能学习到某些语义关系方向。

比如：

男性 → 女性

可能对应某种相对稳定的向量变化。

于是：

king
 ↓
减去某些“男性”关系
 ↓
加上某些“女性”关系
 ↓
靠近 queen

但现代 Transformer 的表示更加上下文化。

同一个词：

bank

在：

river bank

和：

bank account

里面，最终上下文表示可能完全不同。

二十四、静态 Embedding 和上下文 Embedding

教授写：

静态词向量

例如传统 Word2Vec：

“苹果”
永远一个向量

不管：

我吃了一个苹果

还是：

苹果发布了新手机

“苹果”的基础词向量是同一个。

上下文表示

Transformer：

Token Embedding
      ↓
Transformer
      ↓
Contextual Representation

于是：

苹果 + 吃

可能更偏水果意义。

苹果 + iPhone

可能更偏公司意义。

这也是 Transformer 强大的关键之一：

一个 Token 最终的表示，会根据上下文改变。

二十五、PyTorch 中的一个微型 NLP 模型

教授说：

“先不学 Transformer，我们做一个极简文本分类。”

词表：

0 PAD
1 我
2 喜欢
3 PyTorch
4 Java
5 讨厌

模型：

import torch
import torch.nn as nn


class TextClassifier(nn.Module):

    def __init__(self, vocab_size, embed_dim, num_classes, pad_id=0):
        super().__init__()

        self.pad_id = pad_id
        self.embedding = nn.Embedding(
            vocab_size, embed_dim, padding_idx=pad_id
        )

        self.fc = nn.Linear(
            embed_dim,
            num_classes
        )

    def forward(self, token_ids):

        x = self.embedding(token_ids)

        mask = (token_ids != self.pad_id).unsqueeze(-1)
        x = (x * mask).sum(dim=1) / mask.sum(dim=1).clamp_min(1)

        logits = self.fc(x)

        return logits

林默盯住：

mask = (token_ids != self.pad_id).unsqueeze(-1)
x = (x * mask).sum(dim=1) / mask.sum(dim=1).clamp_min(1)

“这是干什么？”

教授说：

“先把所有 Token 向量取平均。”

例如：

[batch, seq_len, embed_dim]

变成：

[batch, embed_dim]

相当于把一句话压成一个向量。

二十六、为什么这个模型很弱

模型：

我 喜欢 PyTorch

从语言模型预训练，走向指令微调、偏好优化与推理能力训练。

第十三天，凌晨一点。

林默终于完成了人生中第一次大语言模型微调。

一张 24GB 的显卡，使用 QLoRA，训练了数千步。

他兴奋地打开测试程序，输入：

请解释 Java HashMap 为什么线程不安全，并给出一个可运行的示例。

模型开始输出：

“HashMap 通过内部 synchronized 机制保证线程安全……”

林默的笑容消失了。

“等等。”

“HashMap 本身不保证线程安全，哪来的内部 synchronized 机制？”

他继续测试：

请解释 Java ThreadLocal 为什么可能发生内存泄漏。

模型回答得很流畅，但混淆了弱引用 Key 与强引用 Value。

再测试一道算法题。

代码能编译，却没考虑边界条件。

林默望着下降的训练 Loss。

Step 100    Loss 2.31
Step 500    Loss 1.42
Step 1000   Loss 0.83
Step 2000   Loss 0.41

“教授，Loss 明明一直在下降。”

“为什么模型还是会回答错误？”

陈教授走到白板前，写下：

训练目标下降≠真实能力一定提升 \boxed{\text{训练目标下降}\ne\text{真实能力一定提升}}

“你让模型学习的，究竟是什么？”

“预测下一个 Token。”

“那你有没有直接教它什么叫事实正确、什么叫按照指令回答、什么叫承认不确定性？”

林默沉默了。

教授继续：

“今天，我们要研究大语言模型的第二阶段。”

预训练让模型学会语言中的广泛规律，而后训练试图把这些能力塑造成更符合目标任务和使用要求的行为。

第一幕：为什么预训练模型不等于助手模型？

一、一个只会续写的学者

教授在终端中写入：

问题：Java HashMap 为什么线程不安全？

一个只经过基础预训练的模型，可能继续生成：

问题：ConcurrentHashMap 为什么线程安全？

问题：Hashtable 和 HashMap 有什么区别？

林默皱眉。

“它怎么不回答？”

教授说：

“因为对一个只学过普通文本续写目标的模型而言，继续生成另一道问题也可能是合理的文本延续。”

预训练目标通常可以写成：

Lpretrain=−∑tlog⁡Pθ(xt∣x<t) L_{\text{pretrain}} = -\sum_t\log P_\theta(x_t\mid x_{<t})

它直接优化的是：

给定前面的 Token，提高训练数据中后续 Token 的预测概率。

它并没有天然规定：

遇到用户提问 → 必须认真回答

遇到编程任务 → 应该给正确代码

不知道答案 → 应该表达不确定性

遇到歧义 → 必要时询问

这些行为可以通过后训练被进一步塑造。

教授画出大模型训练的一条典型路线：

海量预训练语料
        │
        ▼
   Pre-training
        │
        ▼
    Base Model
        │
        ▼
Instruction SFT
        │
        ▼
  Instruct Model
        │
 ┌──────┴──────┐
 ▼             ▼
DPO        RLHF / RL
 │             │
 └──────┬──────┘
        ▼
 Post-trained Model
        │
        ▼
    Evaluation

“注意，”教授说，“这是一种概念化路线，不代表所有现代模型都严格按照这个固定顺序训练。不同方法还可以迭代或组合。”

第二幕：SFT——给模型一本优秀答案集

二、SFT 到底是什么？

教授写：

Supervised Fine-Tuning

监督微调，简称 SFT。

“想象一下，你招聘了一个读过数百万本书的学者。”

“他知识面很广，但不知道公司希望他怎么工作。”

“于是你给他一本工作手册。”

用户提出 Java 问题
       ↓
应该先明确概念
       ↓
再解释原理
       ↓
提供准确的示例
       ↓
必要时说明适用条件

这本手册就是高质量指令数据集的一种类比。

例如：

{
  "messages": [
    {
      "role": "user",
      "content": "什么是 Java ThreadLocal？"
    },
    {
      "role": "assistant",
      "content": "ThreadLocal 提供线程局部变量访问机制，每个线程可以通过同一个 ThreadLocal 对象访问自己的值..."
    }
  ]
}

林默点头。

“也就是把用户问题和优秀回答配成训练样本。”

“对。”

但 SFT 的关键不仅在于有数据。

还在于：

哪些 Token 应该参与 Loss？

三、SFT 和预训练，Loss 是不是完全不同？

林默问：

“之前预训练使用 CrossEntropyLoss。”

“SFT 是不是要换一个特殊的损失函数？”

教授摇头。

“对自回归语言模型，常见 SFT 仍然可以使用下一 Token 预测的交叉熵。”

公式：

LSFT=−∑t∈Alog⁡Pθ(yt∣x,y<t) L_{\text{SFT}} = -\sum_{t\in\mathcal A} \log P_\theta(y_t\mid x,y_{<t})

其中：

  • xx：用户输入及必要的对话上下文。
  • yy：目标助手回答。
  • A\mathcal A：参与损失计算的目标回答位置。

“最大的区别之一，在于训练样本如何组织，以及哪些位置参与训练。”

第三幕：最容易写错的地方：Prompt Mask

四、为什么用户问题通常不应该被当作回答来训练？

教授写出：

<user>
解释 Java HashMap 的扩容机制。
</user>

<assistant>
HashMap 在容量达到阈值时通常会触发扩容……

假设 Tokenizer 已经完成编码。

Input IDs：

[用户问题 Token ...][助手回答 Token ...]

林默问：

“那 labels 不就是把所有 input_ids 向后错位一格吗？”

教授回答：

“基础语言模型可以这么训练。”

“但如果我们的目标是让模型学会生成助手回答，那么一种常见 SFT 策略是：只对助手回答部分计算 Loss。”

他在黑板上写：

输入：

[Prompt Token][Answer Token]


Loss Mask：

[不计算 Loss][计算 Loss]

在 PyTorch 的 CrossEntropyLoss 中，默认有一个非常有用的设置：

ignore_index=-100

如果某个目标位置的 Label 是：

-100

就表示：

这个位置不参与 CrossEntropyLoss。

五、用一个简单例子理解 -100

教授先不用真实 Tokenizer，而是使用数字演示。

假设：

用户问题：[11, 12, 13]

助手回答：[21, 22, 23]

训练序列：

input_ids = torch.tensor([    11, 12, 13, 21, 22, 23])

如果采用完整序列的下一 Token 预测标签：

[12, 13, 21, 22, 23, ...]

但我们希望仅让模型针对助手回答产生的目标 Token 计算损失。

可以概念化成：

上下文位置：

11    12    13    21    22

预测目标：

忽略  忽略  21    22    23

于是：

Labels：

[-100, -100, 21, 22, 23]

林默突然发现：

“第三个位置的输入是用户问题的最后一个 Token。”

“它负责预测助手回答的第一个 Token！”

教授点头。

“这就是需要认真处理 Token 对齐的原因。”

“不同训练框架可能约定 labels 为未移位序列，内部完成 shift，也可能要求你提前移位。不能把两套约定混用。”

六、写一个简化的 PyTorch SFT Loss

假设模型输出：

logits.shape = [B, T, V]

我们使用与完整输入等长、未移位的标签 Tensor，并在计算 Loss 时手动完成移位。上面的五项 Labels 已是移位后的示意；不能直接传给下面这段代码。下面假设 logits.shape=[1,6,V]，且 V 至少为 24。这里 -100 只屏蔽目标监督，不会屏蔽读取上下文的 Attention；输入 Padding 还需要独立的 attention mask。

import torch
import torch.nn.functional as F

# input_ids 的形状是 [B, T]；下面演示一个 6 Token 的样本。
# Prompt 为 [11, 12, 13]，回答为 [21, 22, 23]。
labels = torch.tensor([[-100, -100, -100, 21, 22, 23]], device=logits.device)
shift_logits = logits[:, :-1, :].contiguous()
shift_labels = labels[:, 1:].contiguous()
if not (shift_labels != -100).any():
    raise ValueError("当前 Batch 没有可监督的回答 Token")
loss = F.cross_entropy(
    shift_logits.reshape(-1, shift_logits.size(-1)),
    shift_labels.reshape(-1), ignore_index=-100
)

林默看着：

logits[:, :-1, :]

和：

labels[:, 1:]

立刻想起第十一章。

“还是错位预测！”

“对。”

“只是我们把用户 Prompt 对应的目标位置 Mask 掉，让 Loss 重点监督助手回答。”

教授补充：

“对于多轮对话，还需要明确哪些 assistant 消息参与训练，以及角色标记、结束标记和工具消息如何处理。”

“高质量 SFT 数据管线，往往比单纯写一个训练循环更容易出错。”

第四幕：为什么 Loss 下降，却未必学得更好？

七、模型可能只是在死记硬背

教授再次展示林默的训练曲线。

训练 Loss：

2.31 → 1.42 → 0.83 → 0.41

“你觉得这代表什么？”

林默说：

“模型越来越擅长预测训练集里的答案。”

“很好。”

“但如果这些答案都已经被记住，它是否一定能回答新问题？”

“不一定。”

教授给出例子。

训练集里只有：

Q：HashMap 为什么线程不安全？
A：因为它没有提供完整的并发访问安全保证……

但验证集里是：

Q：两个线程同时修改 HashMap，可能产生什么问题？

这时，模型是否能够解释：

数据竞争

丢失更新

可见性问题

并发结构修改风险

才更接近我们关心的泛化能力。

八、训练集、验证集和测试集应该怎么用？

教授写：

数据集 主要用途
Training 更新模型参数
Validation 选择超参数、检查过拟合、决定训练策略
Test 在模型及评测方案确定后估计最终泛化表现

“如果你反复针对测试集调模型，它实际上也开始影响你的模型选择。”

“那么最终测试结果可能越来越乐观。”

林默点头。

这跟 Coding Agent 的 SWE-bench 评测非常类似。

训练目标只是优化手段，真实任务表现才是最终评价依据。

第五幕：两份答案都正确，应该选择谁？

九、SFT 遇到的新问题

教授写出同一个用户问题：

Java HashMap 为什么线程不安全？

然后给出两个答案。

回答 A：

“HashMap 不是线程安全的。如果多个线程并发修改，可能出现数据竞争和丢失更新。需要根据场景选择同步控制或 ConcurrentHashMap。”

回答 B：

“HashMap 非线程安全。并发修改时可能出现更新丢失、读取到不一致状态等问题。例如，两个线程在缺乏同步的情况下同时进行结构修改，其行为不具备线程安全保证。通常可以使用 ConcurrentHashMap，或者通过外部同步保护共享 HashMap。需要注意，ConcurrentHashMap 也不等于任意复合操作天然原子化。”

教授问：

“哪个更好？”

林默回答：

“B 更详细，还说明了 ConcurrentHashMap 的适用边界。”

教授点头。

“但假设用户只需要一句话的面试答案呢？”

林默思考。

“那 A 可能更合适。”

“正是如此。”

教授写下：

回答质量不仅包含正确性，还可能包含完整性、简洁度、帮助程度、格式和上下文适配性。

而 SFT 只利用某条目标回答直接进行监督，并不天然显式比较不同回答的优劣。

于是一个新的训练目标出现了：

Preference Optimization

偏好优化。

十、Chosen 与 Rejected

教授建立一份训练数据：

{
  "prompt": "解释 Java ThreadLocal 的工作原理。",
  "chosen": "ThreadLocal 通过线程内部维护的 ThreadLocalMap 实现每线程独立存储...",
  "rejected": "ThreadLocal 通过创建一个全局共享变量保证线程安全..."
}

林默看着：

chosen

rejected

“一个是更受偏好的回答。”

“另一个是较差的回答。”

“没错。”

教授说：

“但 chosen 不一定是绝对正确，rejected 也不一定完全错误。”

“它们表示在特定标准下的相对偏好。”

例如：

Prompt
   │
   ├── Answer A
   │      ↓
   │    Chosen
   │
   └── Answer B
          ↓
       Rejected

目标变成：

提高模型对偏好回答的相对倾向。

第六幕：DPO——没有单独奖励模型，也能学习偏好？

十一、Direct Preference Optimization

教授写：

DPO

Direct Preference Optimization

林默问：

“它和 SFT 有什么区别？”

教授回答：

“SFT 让模型提高目标回答的条件概率。”

“DPO 则利用成对偏好数据，优化 chosen 与 rejected 之间的相对关系，并通过参考模型约束偏好变化。”

他画出：

Prompt
             │

“参考模型又是什么？”

教授写下：

→ 当前正在训练的模型

→ 作为对比基准的模型

十二、为什么 DPO 需要 Reference Model？

教授给出一个例子。

对于某个 Prompt：

Chosen：
正确且清晰的回答

Rejected：
错误且冗长的回答

如果只要求：

P(Chosen) > P(Rejected)

看起来很合理。

但教授说：

“我们不希望模型为了满足一些有限的偏好样本，就任意偏离原来学到的大量语言能力。”

“所以 DPO 的典型目标里，会比较当前模型与参考模型对两份回答的相对概率。”

设：

πθ \pi_\theta

表示当前 Policy。

πref \pi_{\text{ref}}

表示参考模型。

DPO 的经典损失可以写成：

LDPO=−log⁡σ(β[log⁡πθ(yw∣x)πref(yw∣x)−log⁡πθ(yl∣x)πref(yl∣x)]) \mathcal L_{\text{DPO}} = -\log\sigma \left( \beta \left[ \log\frac{\pi_\theta(y_w|x)} {\pi_{\text{ref}}(y_w|x)} - \log\frac{\pi_\theta(y_l|x)} {\pi_{\text{ref}}(y_l|x)} \right] \right)

其中：

  • ywy_w：chosen。
  • yly_l：rejected。
  • β\beta：控制偏好优化中相对参考模型变化的尺度。
  • σ\sigma：Sigmoid。

林默盯着公式。

“看着还是复杂。”

教授说：

“那我们把它拆成三个数字。”

十三、把 DPO 公式翻译成人话

定义：

rw=log⁡πθ(yw∣x)−log⁡πref(yw∣x) r_w= \log\pi_\theta(y_w|x) - \log\pi_{\text{ref}}(y_w|x)

rl=log⁡πθ(yl∣x)−log⁡πref(yl∣x) r_l= \log\pi_\theta(y_l|x) - \log\pi_{\text{ref}}(y_l|x)

于是：

L=−log⁡σ(β(rw−rl)) L=-\log\sigma(\beta(r_w-r_l))

林默终于看懂了。

“所以核心是在比较：”

当前模型相对参考模型
对 Chosen 提高了多少倾向

减去

当前模型相对参考模型
对 Rejected 提高了多少倾向

“对。”

如果这个差值变大，DPO Loss 通常会下降。

教授强调：

“这里比较的是完整回答的条件对数概率，而不是简单地只比较某一个 Token 的 Softmax 值。”

本节指经典、带参考模型的 DPO。参考模型提供相对基准，但不是对所有行为变化的硬性保证；DPO 变体可能采用不同参考机制。完整回答的 logp 应按回答 Token 的条件 logp 求和，排除 Prompt 与 PAD。

十四、用 PyTorch 手写 DPO 核心 Loss

教授打开编辑器：

import torch
import torch.nn.functional as F

def dpo_loss(policy_chosen_logp, policy_rejected_logp,
             ref_chosen_logp, ref_rejected_logp, beta=0.1):
    if beta <= 0:
        raise ValueError('beta must be positive')
    policy_logratio = policy_chosen_logp - policy_rejected_logp
    ref_logratio = (ref_chosen_logp - ref_rejected_logp).detach()
    return -F.logsigmoid(beta * (policy_logratio - ref_logratio)).mean()

林默一眼认出了：

F.logsigmoid()

“就是之前学过的 Sigmoid 的对数形式。”

“对。”

“PyTorch 把很多复杂公式拆开之后，其实依然是普通 Tensor 运算。”

教授提醒：

“这只是经典 DPO 核心损失的示例。完整训练还需要正确计算每个回答的 Token 对数概率、Mask 掉 Prompt 和 Padding、处理序列长度、参考模型前向，以及注意数值稳定性。”

十六、Reward Model 是什么？

假设模型针对同一个问题生成两个答案：

Answer A：
HashMap 是线程安全的，因为……

Answer B：
HashMap 不保证线程安全，因为……

人类标注者更偏好 B。

我们可以训练一个模型：

输入：

Prompt + Answer

输出：

一个评分

例如：

Reward Model

Answer A → -1.2

Answer B →  2.4

林默问：

“所以 Reward Model 就像一个评分老师？”

“可以这么理解。”

“但评分值不是一个客观真理，它是根据训练反馈学习出来的估计。”

教授写：

Rϕ(x,y) R_\phi(x,y)

表示奖励模型对问题 xx 和回答 yy 给出的分数。

然后强化学习希望：

max⁡θEy∼πθ[Rϕ(x,y)] \max_\theta \mathbb E_{y\sim\pi_\theta} [R_\phi(x,y)]

即：

让当前模型生成更容易获得高奖励的回答。

但如果只追逐奖励，也会出问题。

第八幕：奖励黑客：为什么模型会钻评分规则的漏洞？

十七、一个危险的实验

教授给模型设计了一条简单奖励规则。

如果答案包含：

“详细解释”

奖励 +1

一开始，模型确实更喜欢给出详细解释。

但训练继续之后，模型开始生成：

详细解释，详细解释，详细解释……

林默愣住。

“它在刷奖励？”

教授点头。

“这就是 Reward Hacking 的一个简化例子。”

当奖励信号不能准确反映真实目标时，模型可能优化评分规则，而不是优化人类真正想要的结果。

在 Coding Agent 场景也可能出现类似问题。

例如：

奖励：
只要测试通过就给高分

如果评测环境存在缺陷，Agent 可能找到绕过测试的方式，而不是正确实现需求。

因此：

奖励函数设计和评测环境可靠性，是强化学习训练中极其重要的工程问题。

十八、为什么 RLHF 常常需要约束模型不要偏离太远？

教授写：

max⁡θE[R(x,y)−βDKL(πθ∥πref)] \max_\theta \mathbb E \left[ R(x,y) - \beta D_{KL} \left( \pi_\theta\Vert\pi_{\text{ref}} \right) \right]

林默看向：

DKL D_{KL}

“这是 KL 散度？”

“对。”

“它可以衡量两个概率分布之间的差异。”

教授解释：

Reward
    ↓
鼓励模型更符合偏好


KL Penalty
    ↓
抑制模型无约束地偏离参考策略

比如：

只提高奖励
    ↓
可能利用奖励漏洞
    ↓
生成异常内容

加入合适的约束，可以降低这种偏移风险。

但也要注意：

“KL 约束不是奖励黑客问题的万能解法，过强约束还可能限制模型改善。”

第九幕：PPO 到底在做什么？

十九、Policy Gradient：生成也是一种决策过程

教授说：

林默点头。

“比如智能体控制角色移动。”

当前状态：
已有 Prompt 和生成前缀
        │
        ▼
动作：
选择下一个 Token
        │
        ▼
新状态：
前缀追加 Token
        │
        ▼
继续选择下一个 Token

在这个框架下：

  • State：当前上下文。
  • Action：选择下一个 Token。
  • Policy：语言模型的条件概率分布。
  • Reward：根据生成结果获得的反馈。

林默恍然大悟。

二十、PPO 为什么要限制更新幅度？

PPO：

Proximal Policy Optimization

教授画了一条简单的优化路线。

旧 Policy
    │
    ▼
生成回答
    │
    ▼
获得 Reward
    │
    ▼
估计 Advantage
    │
    ▼
更新 Policy

“但如果一次更新幅度太大，模型生成策略可能突然发生剧烈变化。”

“PPO 的经典 Clipped Objective，正是为了限制策略更新中的某些过大变化。”

公式：

LCLIP=E[min⁡(rtAt,clip(rt,1−ϵ,1+ϵ)At)] L^{CLIP} = \mathbb E \left[ \min \left( r_tA_t, clip(r_t,1-\epsilon,1+\epsilon)A_t \right) \right]

其中：

rt=πθ(at∣st)πold(at∣st) r_t= \frac{\pi_\theta(a_t|s_t)} {\pi_{\text{old}}(a_t|s_t)}

林默问：

“这个比例什么意思？”

教授回答：

“它比较某个动作在新旧策略下的概率。”

比如：

旧模型：
选择某 Token 的概率 = 0.2

新模型：
选择该 Token 的概率 = 0.8

那么：

rt=0.80.2=4 r_t=\frac{0.8}{0.2}=4

“变化非常大。”

“PPO 的 Clip 机制会限制这种比例变化对目标函数带来的进一步优化激励。”

教授提醒：

“这不表示 PPO 在数学上保证每次策略变化绝不会超过阈值，它只是用裁剪目标抑制过大的更新诱因。”

二十六、五道理解测试

第十三章随堂测试

1. SFT 中把 Prompt 对应的 Label 设为 -100，主要是为了什么？

禁止模型读取 Prompt

使相应目标位置不参与 CrossEntropyLoss

把 Prompt 自动转成 Embedding

2. DPO 的经典目标主要利用什么数据？

只有原始预训练文本

Chosen / Rejected 成对偏好数据

只有模型参数数量

3. Reward Model 的评分应该如何理解？

绝对客观的正确性证明

根据反馈数据学习出来的评分估计

与训练数据无关的固定数学真理

4. PPO 中的 Clip 机制主要解决什么问题？

抑制策略更新中的过大变化激励

减少模型词表长度

保证所有生成结果都正确

5. 为什么不能只看 SFT Loss 判断模型有没有变强？

Loss 不可以计算

Loss 只衡量训练目标，不能充分反映未见任务上的表现

因为 SFT 不使用反向传播

展开本章五道题的参考答案

  1. 使相应目标位置不参与交叉熵；模型依然能读取 Prompt 上下文。

  2. 同一 Prompt 下的 chosen/rejected 成对偏好数据。

  3. 根据反馈数据学到的评分估计，不能当作正确性的证明。

  4. 抑制过大策略变化带来的进一步优化激励，不是硬性限制所有更新。

  5. Loss 只度量指定目标，仍需在独立、未见任务上评估质量和泛化。

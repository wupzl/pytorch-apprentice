凌晨三点。

实验室的灯依旧亮着。

林默坐在一台价值不菲的工作站前，盯着终端里的一行红字。

torch.OutOfMemoryError:
CUDA out of memory.

他已经尝试了三次。

第一次，把 Batch Size 从 16 改成 8。

第二次，从 8 改成 2。

第三次，直接改成 1。

可模型还是无法正常训练。

“教授，我已经把 Batch Size 降到 1 了！”

林默指着屏幕。

“为什么还是显存不足？”

陈教授看了一眼配置：

model = MiniGPT(vocab_size=50000, d_model=4096, num_heads=32, num_layers=32, block_size=4096)

又看了看显卡：

NVIDIA GPU
VRAM: 24 GB

教授没有修改代码。

而是在白板上写下一句话：

模型能放进显存，不代表模型能够在这张显卡上训练。

林默愣住。

“这两件事情有区别？”

教授拿起粉笔。

“区别大得多。”

“今天，我们不研究如何让模型变聪明。”

“我们研究如何让它活下来。”

第一幕：24GB 显存为什么不够？

一、模型参数只是显存战争的第一支军队

教授问：

“一个模型有 70 亿参数，也就是 7B。”

“如果每个参数使用 FP32 保存，需要多少内存？”

林默想起第六章。

“FP32 一个数字占 4 字节。”

于是：

7×109×4=28×109 Bytes 7\times10^9\times4 = 28\times10^9\text{ Bytes}

约等于：

28 GB \boxed{28\text{ GB}}

这里的 GB 是十进制单位；换成二进制 GiB，大约是 26.1 GiB。

林默点头。

“所以 7B 模型使用 FP32，光权重就需要约 28GB。”

“对。”

“那换成 FP16 呢？”

7×109×2=14 GB 7\times10^9\times2 = 14\text{ GB}

林默兴奋起来。

“14GB！”

“24GB 显卡应该可以训练了吧？”

教授摇头。

“你忘了训练需要什么。”

他在白板上写出四支军队。

┌──────────────────────────────┐
│           GPU VRAM           │
├──────────────────────────────┤
│                              │
│  第一支军队：Model Weights   │
│           模型权重            │
│                              │
├──────────────────────────────┤
│                              │
│  第二支军队：Gradients       │
│           参数梯度            │
│                              │
├──────────────────────────────┤
│                              │
│  第三支军队：Optimizer State │
│           优化器状态          │
│                              │
├──────────────────────────────┤
│                              │
│  第四支军队：Activations     │
│           中间激活            │
│                              │
├──────────────────────────────┤
│      CUDA 工作区与临时缓存    │
└──────────────────────────────┘

“而你刚刚只计算了第一支军队。”

二、AdamW 为什么这么吃显存？

教授打开之前的代码：

optimizer = torch.optim.AdamW(    model.parameters(),    lr=3e-4)

“还记得 AdamW 吗？”

林默回答：

“它会保存梯度的一阶矩和二阶矩估计。”

“没错。”

假设我们进行常规 FP32 全参数训练，暂时不考虑激活和其他开销。

每个参数可能涉及：

内容 每参数字节数
FP32 参数 4
FP32 梯度 4
AdamW 一阶矩 4
AdamW 二阶矩 4
合计 16

所以 7B 模型：

7×109×16=112 GB 7\times10^9\times16 = 112\text{ GB}

7B 模型：简化 FP32 AdamW 状态预算（十进制 GB）

状态 每参数字节 7B 参数理论占用
FP32 权重 4 28 GB
FP32 梯度 4 28 GB
FP32 一阶矩 4 28 GB
FP32 二阶矩 4 28 GB
合计 16 112 GB（约 104.3 GiB）

只计算指定状态，不含激活、临时工作区、缓存及其他开销；不是所有混合精度实现的通用公式，也不是显存实测。

林默望着自己的显卡。

“24GB……”

“连这里的四分之一都不到。”

教授点头。

“而且这个 112GB 并不是所有混合精度训练的固定显存公式。”

“不同的混合精度方案，可能保存不同精度的参数副本、梯度和优化器状态。”

“实际内存预算必须根据具体实现计算。”

三、为什么 Batch Size 降到 1 也不一定有用？

林默突然明白了。

“Batch Size 主要影响中间激活和输入数据。”

“但是模型参数和优化器状态，不会因为 Batch Size 从 16 降到 1，就跟着缩小十六倍！”

教授点头。

这就是大模型训练中非常重要的区分：

参数相关显存主要取决于模型大小、数据精度以及优化器设计。

激活相关显存主要受到 Batch Size、Sequence Length、隐藏维度、网络层数和算子实现影响。

所以：

显存不足
    │
    ├── 模型权重过大？
    │      ↓
    │   量化、分片、卸载等
    │
    ├── 梯度/优化器状态过大？
    │      ↓
    │   LoRA、优化器状态分片等
    │
    ├── 中间激活过大？
    │      ↓
    │   减小 Batch、Checkpointing
    │
    └── Attention 中间计算过大？
           ↓
        FlashAttention / SDPA

教授说：

“你必须先知道是谁占用了显存。”

“才能选择正确的武器。”

第二幕：混合精度——让数字穿上轻甲

四、FP32、FP16、BF16 到底是什么？

教授在白板上写下三个名字。

FP32

FP16

BF16

林默说：

“都是浮点数。”

“但分别有什么区别？”

教授回答：

“浮点数在计算机里，通常不是直接存储一个普通的十进制小数。”

“它会使用符号位、指数和有效数字字段来近似表示实数。”

三种格式的典型布局：

格式 总位数 符号位 指数位 尾数字段
FP32 32 1 8 23
FP16 16 1 5 10
BF16 16 1 8 7

尾数字段不包含规范化浮点数的隐含前导有效位。

林默仔细看。

“FP16 和 BF16 都是 16 位。”

“但 FP16 给了尾数更多位。”

“BF16 给了指数更多位？”

教授点头。

五、指数位与尾数位分别决定什么？

教授拿出一个比喻。

“假设你要记录天文学距离和实验室测量数据。”

“指数位更多，意味着能表示更大或更小量级的数字。”

“有效数字位更多，意味着在某个量级附近能区分更细小的数值差异。”

因此：

格式 存储空间 动态范围 有效精度
FP32 4 字节 大 高
FP16 2 字节 较窄 中等
BF16 2 字节 接近 FP32 的指数范围 较低

林默问：

“所以 BF16 更适合大模型训练？”

教授说：

“在支持 BF16 高效运算的硬件上，它通常是非常有吸引力的选择。”

“因为它具有接近 FP32 的动态范围，能减少 FP16 常见的数值溢出或下溢风险。”

“但 BF16 不是万能的。它的有效精度比 FP16 更低，某些操作仍需更高精度。”

六、为什么不能把所有东西都强制转成 FP16？

林默敲下：

model = model.half()

又把输入转成 FP16。

“这样不就省显存了？”

教授立即阻止。

“这属于手动降低参数精度，不等于安全的自动混合精度训练。”

因为有些操作适合低精度，例如：

大规模矩阵乘法

但有些操作对数值范围和精度更敏感，例如某些：

归一化
损失计算
归约计算

如果全部粗暴地使用 FP16，可能出现：

Loss = NaN

Gradient = Inf

训练突然发散

教授写下：

Automatic Mixed Precision

简称：

AMP。

“它的核心思想是，让不同操作根据实现策略使用适合的数值精度，而不是所有运算都一刀切。”

七、PyTorch 的 autocast

教授开始编写一个标准 CUDA 混合精度训练循环：

# 需要支持 BF16 的 CUDA GPU，以及已经定义的 MyModel、loader、loss_fn。
device = torch.device("cuda")
model = MyModel().to(device)
optimizer = torch.optim.AdamW(model.parameters(), lr=3e-4)
model.train()
for x, y in loader:
    x, y = x.to(device), y.to(device)
    optimizer.zero_grad(set_to_none=True)
    with torch.autocast(device_type="cuda", dtype=torch.bfloat16):
        logits = model(x)
        loss = loss_fn(logits, y)
    loss.backward()
    optimizer.step()

林默盯着：

with torch.autocast(device_type="cuda", dtype=torch.bfloat16):
    ...  # 在此执行前向传播和 Loss 计算

“所以在这个区域里，PyTorch 会按 AMP 的规则选择运算精度？”

“对。”

“注意，这不是把模型所有权重永久变成 BF16。”

“常见 AMP 训练仍然会保留 FP32 参数，优化器也可能使用 FP32 状态。”

这与：

model.to(torch.bfloat16)

并不是一回事。

八、GradScaler 为什么存在？

林默翻看其他人的代码。

突然发现：

scaler = torch.amp.GradScaler("cuda")

“教授，为什么有些训练还多一个 GradScaler？”

教授在黑板上写：

原始梯度：

0.00000001

“如果 FP16 无法充分表示某些非常小的梯度，它们可能下溢为零。”

“于是我们可以在反向传播之前，暂时把 Loss 放大。”

例如：

L′=1024L L'=1024L

那么：

∂L′∂w=1024∂L∂w \frac{\partial L'}{\partial w} = 1024\frac{\partial L}{\partial w}

林默明白了。

“这样梯度也放大了。”

“对。”

“然后参数更新之前，再把梯度缩回去。”

这就是 Loss Scaling 的核心思路。

FP16 AMP 训练中常见：

# 假设 model、optimizer 已创建并位于 CUDA，loader 与 loss_fn 已定义。
scaler = torch.amp.GradScaler("cuda")
model.train()
for x, y in loader:
    x, y = x.to("cuda"), y.to("cuda")
    optimizer.zero_grad(set_to_none=True)
    with torch.autocast(device_type="cuda", dtype=torch.float16):
        logits = model(x)
        loss = loss_fn(logits, y)
    scaler.scale(loss).backward()
    scaler.step(optimizer)
    scaler.update()

教授说：

“GradScaler 还会监测非有限梯度，并在必要时跳过参数更新和调整缩放比例。”

“BF16 通常不需要通过这种方式解决 FP16 的梯度下溢问题。”

林默在笔记中写下：

autocast 负责运算精度策略；GradScaler 主要服务于 FP16 梯度数值稳定性。

第三幕：梯度累积——没有大货车，就多运几趟

九、Batch Size 为什么这么重要？

教授写：

目标：

Batch Size = 64

但是 GPU 只能装下：

Batch Size = 4

林默问：

“那我是不是没办法训练？”

教授笑了。

“你想想，训练过程中最关键的参数更新发生在哪一步？”

林默回答：

optimizer.step()

“对。”

“那假设我们不每处理一批就更新，而是先累积多个 Batch 的梯度呢？”

林默突然想起第一章。

PyTorch 的 .grad 默认会累加！

十、原来梯度累积利用的是第一章的知识

正常训练：

Batch 1
   ↓
backward()
   ↓
optimizer.step()

Batch 2
   ↓
backward()
   ↓
optimizer.step()

而梯度累积：

Batch 1
   ↓
backward()
   │

十一、为什么 Loss 要除以累积步数？

假设：

micro_batch_size = 4

accumulation_steps = 16

有效 Batch Size：

4×16=64 4\times16=64

正常情况下，我们希望得到 64 个样本的平均梯度：

g=164∑i=164gi g=\frac1{64}\sum_{i=1}^{64}g_i

每个 Micro-Batch 的 Loss 如果已经是四个样本的平均值，那么它的梯度是：

gj=14∑i∈Bjgi g_j=\frac14\sum_{i\in B_j}g_i

16 个 Batch 梯度直接累加：

∑j=116gj \sum_{j=1}^{16}g_j

会比所需的整体平均梯度大 16 倍。

因此：

loss = loss / accumulation_steps

教授写：

# 这里恰好累积 16 个同样大小、等权的 Micro-Batch。
accumulation_steps = 16
optimizer.zero_grad(set_to_none=True)
for step in range(accumulation_steps):
    x, y = get_batch()
    x, y = x.to(device), y.to(device)
    logits, loss = model(x, y)
    (loss / accumulation_steps).backward()
optimizer.step()

林默点头。

“这样累积的梯度才对应整体平均梯度。”

教授补充：

“这个例子假设各 Micro-Batch 大小相同，Loss 按样本平均，且没有影响 Batch 间等价性的特殊操作。”

“如果最后一批大小不同，或者 Loss 按 Token 平均且有效 Token 数不同，应该按实际样本数或有效 Token 数加权。”

十二、把训练配置写成一张估算表

“先手算几组配置，看看我们到底改变了什么。”

每卡 Micro-Batch 累积步数 数据并行 GPU 数 每次更新的有效样本数
4 16 1 64
2 32 1 64
4 8 2 64

有效样本数 = 每卡 Micro-Batch × 累积步数 × 数据并行卡数。

这张表不是显存测量结果。前两组虽有相同的有效样本数，单次激活需求与运行开销可能不同；模型权重和优化器状态也不会随 Micro-Batch 同比例缩小。第三组假设各数据并行副本处理等量独立样本，不能把张量并行卡数直接代入。

对于变长文本，Loss 若按有效 Token 平均，应在整个累积窗口按有效 Token 总数归一化；简单把每个 Micro-Batch 的均值除以累积步数，可能产生不同的加权。遍历 DataLoader 时，最后不足一个累积窗口的数据也应提交更新，并按实际样本或 Token 数归一化。配合 AMP 时，应在完整窗口累积结束后再 unscale、裁剪、step 与更新 scaler。

import math
import torch
import torch.nn as nn
import torch.nn.functional as F

class LoRALinear(nn.Module):
    def __init__(self, original_linear, rank=16, alpha=32):
        super().__init__()
        if rank < 1:
            raise ValueError('rank must be positive')
        self.original = original_linear
        for param in self.original.parameters():
            param.requires_grad_(False)
        self.scaling = alpha / rank
        # Follow the original layer's dtype and device.
        weight = original_linear.weight
        self.lora_A = nn.Parameter(weight.new_empty(rank, original_linear.in_features))
        self.lora_B = nn.Parameter(weight.new_zeros(original_linear.out_features, rank))
        nn.init.kaiming_uniform_(self.lora_A, a=math.sqrt(5))

    def forward(self, x):
        delta = F.linear(F.linear(x, self.lora_A), self.lora_B)
        return self.original(x) + self.scaling * delta

林默看着：

教授点头。

初始化时 B=0，因此普通损失的首步反传通常先给 B 非零梯度，A 的该项梯度为零；B 更新后，A 才开始获得相应梯度。这不等于 A 永远不学习。

林默看着表格。

“它是量化与 LoRA 结合的训练方案。”

“正确。”

第八幕：FlashAttention——不改变答案，改变计算方式

三十、另一场显存灾难：Attention Matrix

林默以为问题已经解决。

他将模型换成 QLoRA。

显存占用降低了不少。

但当他把：

Sequence Length = 2048

改成：

Sequence Length = 16384

训练又开始出现显存压力。

教授问：

“还记得第九章 Self-Attention 的复杂度吗？”

林默回答：

O(n2) O(n^2)

“没错。”

教授写：

Attention(Q,K,V)=softmax(QKTdk)V Attention(Q,K,V)= softmax\left(\frac{QK^T}{\sqrt{d_k}}\right)V

“如果按最直接的方式实现，需要产生一个很大的注意力分数矩阵。”

假设：

seq_len = 16384

那么单个 Attention Head 的分数矩阵：

16384×16384 16384\times16384

约有：

268,435,456 268,435,456

个元素。

如果每个元素使用 2 字节保存：

268,435,456×2=536,870,912 Bytes 268,435,456\times2 = 536,870,912\text{ Bytes}

也就是单个 Head 的一份这种矩阵就约占：

512 MiB 512\text{ MiB}

教授提醒：

“这只是针对一种显式矩阵表示的估算，并不是所有 Attention 实现都会把完整矩阵存下来。”

“但它已经足以说明，为什么长上下文会给朴素 Attention 带来巨大压力。”

三十一、FlashAttention 的核心不是换公式

林默问：

“那 FlashAttention 是不是把 Attention 改成 O(n) 了？”

教授摇头。

“这是一个非常重要的误区。”

“FlashAttention 的关键优势，并不是把标准精确 Attention 的主要算术复杂度从二次方变成线性。”

“它主要通过分块计算和 IO-aware 算法，减少高带宽显存与片上快速存储之间的数据搬运，并避免显式存储完整的 Attention 矩阵。”

教授画：

朴素实现：

Q × Kᵀ
   ↓
生成完整 Scores
   ↓
写入显存
   ↓
读取 Scores
   ↓
Softmax
   ↓
写入显存
   ↓
读取概率矩阵
   ↓
乘 V
   ↓
Output

FlashAttention：

Q / K / V
    ↓
按 Tile 分块
    ↓
尽可能在片上快速存储中完成局部计算
    ↓
在线更新 Softmax 统计量与输出累加
    ↓
输出最终结果

林默突然反应过来。

“也就是说，真正昂贵的不只是乘法。”

“还包括把巨大的中间矩阵反复搬进搬出显存。”

教授点头。

三十二、为什么它能够不保存完整 Softmax 矩阵？

林默追问：

“可是 Softmax 不是需要一整行的所有分数才能计算分母吗？”

教授写：

softmax(zi)=ezi∑jezj softmax(z_i)=\frac{e^{z_i}}{\sum_j e^{z_j}}

“传统思维会先算出整行，再算总和。”

“但可以使用在线 Softmax 算法，在处理分块时维护运行中的最大值与归一化统计量。”

“这样就能分块累积最终结果，而不必为每个 Attention Head 显式保存完整的 N×NN\times N 概率矩阵。”

教授强调：

FlashAttention 计算的是标准 Attention 的数学目标，允许正常浮点舍入误差，但通过改变计算顺序和数据搬运方式提高效率。

三十三、PyTorch 里怎么用 FlashAttention？

教授打开编辑器。

import torch
import torch.nn.functional as F

# Q, K, V 应为 [batch, heads, seq_len, head_dim]。
output = F.scaled_dot_product_attention(
    Q, K, V, is_causal=True, dropout_p=0.0
)

林默问：

“就这一行？”

教授回答：

“PyTorch 的 scaled_dot_product_attention 可以根据设备、数据类型、形状和后端条件选择不同的 Attention 实现，包括受支持环境中的高效融合内核。”

“但不能认为只要调用这个 API，就一定使用了某个特定版本的 FlashAttention。”

“实际需要确认后端支持情况和性能分析结果。”

教授特别补充：

“这里如果使用 dropout_p，要显式按训练/推理状态设置。这个函数不会仅因为外层模型进入 eval() 就自动将传入的 Dropout 概率改为零。”

例如：

dropout_p = 0.1 if self.training else 0.0
output = F.scaled_dot_product_attention(
    Q, K, V, is_causal=True, dropout_p=dropout_p
)

对于只有一张 24GB 显卡的情况，优先考虑在已有开源模型上进行 QLoRA/SFT，而不是从零预训练 7B 模型。

原因很简单：

从零预训练不仅存在显存问题，还需要巨量高质量数据、计算资源和训练工程能力。即使利用各种节省显存技术，一张消费级显卡也不意味着能够以合理成本完成 7B 级模型的充分预训练。

三十六、实际工程中，怎么接入 QLoRA？

教授打开一个新的 Python 文件。

“今天我们不再手工为 7B 模型编写每一层。”

“PyTorch 负责底层张量与自动求导，实际微调通常会配合 Hugging Face Transformers、PEFT 和 bitsandbytes 等工具。”

下面是一个简化的模型加载与 LoRA 配置示例。它需要兼容的 CUDA 环境、已安装的相关依赖，以及用户选定的可访问模型。

# 配置骨架：需要兼容 GPU、依赖和实际模型 ID，不是完整训练脚本。
import torch
from transformers import AutoModelForCausalLM, BitsAndBytesConfig
from peft import LoraConfig, get_peft_model, prepare_model_for_kbit_training

model_id = "your-compatible-7b-model"  # 替换为可访问且许可适用的模型
if not torch.cuda.is_available():
    raise RuntimeError("此示例按单张 CUDA GPU 配置")
compute_dtype = torch.bfloat16 if torch.cuda.is_bf16_supported() else torch.float16
quant_config = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_compute_dtype=compute_dtype,
    bnb_4bit_use_double_quant=True,
)
model = AutoModelForCausalLM.from_pretrained(
    model_id, quantization_config=quant_config,
    device_map={"": torch.cuda.current_device()},  # 单卡训练，不使用推理自动卸载
)
model.config.use_cache = False
model = prepare_model_for_kbit_training(model)
lora_config = LoraConfig(
    r=16, lora_alpha=32, target_modules="all-linear",
    lora_dropout=0.05, bias="none", task_type="CAUSAL_LM",
)
model = get_peft_model(model, lora_config)
model.print_trainable_parameters()

林默看到：

教授回答：

“但不同模型架构和软件版本可能存在兼容性差异，实际训练前需要检查目标模块。”

然后执行：

三十九、面试与实际开发中最容易混淆的五个问题

训练工程理解测试

1. LoRA 将某层可训练参数减少 99%，是否意味着整张 GPU 的显存占用也降低 99%？

是

否，基础权重和激活等依然占显存

2. 梯度累积最主要解决什么问题？

减少单次 Micro-Batch 的激活内存需求

将全部模型权重转换成 INT4

完全消除梯度噪声

3. Activation Checkpointing 的主要代价是什么？

必须降低模型层数

反向传播时进行额外重计算

无法执行反向传播

4. QLoRA 经典方案主要训练哪部分？

全部量化权重

冻结基础权重上的 LoRA 适配器

Tokenizer 的词表

5. FlashAttention 的核心优化是什么？

将标准 Attention 数学目标替换成线性近似

主要减少 Attention 的中间存储和数据搬运

消除 Transformer 对 GPU 的需求

展开本章五道题的参考答案

  1. 否。减少的是适配器对应的可训练参数，基础权重、激活与临时工作区仍占内存。

  2. 减小每次 Micro-Batch 的激活需求，在多次反向后再更新一次参数。

  3. 反向时额外重计算，以时间换空间。

  4. 冻结量化基础权重，训练 LoRA 适配器等选定的额外参数。

  5. 主要减少标准精确 Attention 的中间存储与数据搬运，并非线性近似。
